# Harness gates

Deterministic quality gates shipped with the afk plugin. All gates run against the repo the session works in (`git rev-parse --show-toplevel`); the Maven/format gates no-op outside a core-services-shaped checkout (no `all-modules-pom.xml` at root ⇒ silent allow).

**Where each gate fires.** Three surfaces, wired differently:

- **Stop** — one hooks.json entry, `stop-gates.sh`, which runs the cheap gates (wiring, skill-registry, codex-drift, genericity) in a single process. The adopted harness Stop gates (`java-rules-gate.sh`, `i18n-parity-gate.sh`) stay separate entries because they live in another tree.
- **Commit** — `precommit-gates.sh` runs the expensive code gates (maven-compile, java-format, ui-lint) from the `pre-commit` git hook that `install-git-hooks.sh` installs, for **agent-driven commits only**.
- **PreToolUse / on demand** — unchanged (`lavish-*.sh`, the adopted guards, `app-start-gate.sh`, `mutation-probe.sh`).

**Cost model — subprocess count, not algorithm.** On Windows/git-bash a spawn costs ~0.5–2s (MSYS fork emulation) against ~20–40ms for a native Windows spawn, and degrades under load. A gate's latency is therefore roughly `spawns × that number`, which is why the design rules below matter more than any per-gate cleverness:

- The change set is derived **once per Stop** (`gate-context.sh`) and shared; no gate runs `git status` or hashes a file itself. Scope tests (`gate_ctx_filter` / `gate_ctx_any`) are bash pattern matches, so "no `.java` changed" costs nothing.
- A gate is **entered only when the change set holds a path it could gate** (scope-driven dispatch in `stop-gates.sh`). A gate that judges the *branch* rather than the worktree (registry vs disk, generated Codex layer, added prose) is dispatched on the working-tree list **plus** the committed list (`gate_ctx_branch`) — testing only the worktree stops gating a change at the moment it is committed, which is when it matters most.
- A tree identical to the last **all-green** Stop skips every gate (`.gate-cache/.last-stop`). A blocked verdict never short-circuits — an unchanged tree that blocked must block again. A gate that **crashes** (any exit but 0/2, or a failed source) never blocks, but that Stop records no all-green stamp — the next turn re-runs the suite instead of inheriting a green it didn't earn.
- Per-gate pass caches are keyed on **that gate's own inputs** (`gate_cache_key <gate> <glob>…`), so editing a spec file does not re-run the plugin-registry gates.
- New loops must not spawn per file or per line. Batch instead: one `git grep` for all tokens, one `git hash-object --stdin-paths` for all files, one `awk` pass over a stream. A per-item probe that must read the file (an annotation check, a ledger lookup) belongs **after** the batched pass, where it sees only the few items the batch could not clear — and a ledger or lookup table is read once into a variable, never grepped per item.
- Watch the loop shape too, not just the spawns: a `while read … <<<"$blob"` nested inside a per-candidate loop re-materialises the here-string every iteration. Fold the blob into an associative array in one pass and look up. On a branch carrying 150 new files that alone was 29s of the wiring gate's 52.

**Adopted harness gates.** Four gates are registered here but live in
`tools/payable/ai-agents/harness/hooks/` (their one home, shared with the
`code-quality/` assets they read and the generated Codex layer that invokes the
same scripts): `crowdstrike-guard.sh` + `explore-counter.sh` (PreToolUse) and
`java-rules-gate.sh` + `i18n-parity-gate.sh` (Stop). `hooks.json` invokes them
via `${CLAUDE_PROJECT_DIR}` (existence-guarded, so the plugin stays inert in a
repo without them) rather than `${CLAUDE_PLUGIN_ROOT}` — directory-source
plugins are snapshotted at install, and these gates must track the checkout,
not the snapshot. Their escape hatch is the harness one: `.claude/.gate-disabled`
(no `hooks/` segment). The standalone `payable-harness` plugin that used to
carry them is retired (its `.claude-plugin/` manifests and `hooks/hooks.json`
are deleted) — this plugin is the single registration surface; anyone still
carrying an old `payable-harness` install should uninstall it.

Rules:

- **`branch-name-gate.sh` is a git hook, not an agent-harness hook** — not wired into `hooks.json`; it runs inside git itself on ref updates, which is what catches *every* creation path an agent uses, no shell-command parsing. Enforcement scope (agent-only markers, creation-only, remote-DWIM allowance) and escape hatches (`AFK_SKIP_BRANCH_CHECK=1`, `git config afk.branchNameGate false`, removal): script header. Installation (`SessionStart` runs `install-git-hooks.sh --quiet`, so enabling the plugin is the whole opt-in; idempotent / self-scoping / worktree-safe / non-destructive; fallbacks: `/afk:setup` register H5 or a manual run): `install-git-hooks.sh` header. That installer now places **two** hooks — `reference-transaction` (branch names) and `pre-commit` (the code gates); both follow the same never-clobber rule.
- **Caveat — agent-launched IDE/terminal.** The marker propagates to child processes, so if an agent launches IntelliJ or a shell (e.g. `create-worktree --open`), branch creation *within that launched process* inherits the agent marker and is still gated. A terminal/IDE you started yourself is unaffected. Use the bypass or config-disable in the rare launched-process case.

- Escape hatch for all Stop gates: create `.claude/hooks/.gate-disabled` **in the repo being gated** (leave a reason inside; delete to re-enable).
- **Provider shim.** `hooks/lib/provider.sh` is the one home for provider-specific surface (Claude Code vs OpenAI Codex CLI) — detection, paths, envelope parsing, decision emission, block contract, the synced harness copy: its header. Hooks touching any of that source it; gate logic stays provider-free. Smoke tests: `bash tools/payable/ai-agents/codex-sync/tests/hook-smoke.sh` (every envelope-consuming hook under both provider modes).
- **Shared context.** `gate-context.sh` derives the change set once per Stop (`AFK_CTX_CHANGED` / `_NEW` / `_LIVE` / `_HASHES` / `_TREE`) and every gate reads it — contract, variables (deliberately unexported — the lists are unbounded and would ride every native child's environment), and the fork budget in its header. The tree digest also folds in the gitignored wiring IOU ledger, so editing `.claude/wiring-ious.md` busts the short-circuit and wiring's cache like any tracked change. `gate_ctx_build_staged` is the commit-time variant (scope = staged paths, content = working tree). Merge-base (`gate_ctx_mergebase`) and the committed-change list (`gate_ctx_branch` → `AFK_CTX_BRANCH`) are lazy, so a turn that short-circuits pays for neither. `AFK_GATE_CTX_DISABLE=1` forces a rebuild per call.
- **Pass cache.** Gates remember their last **pass** under `.claude/hooks/.gate-cache/` in the gated repo (`gate-cache.sh` header: key shape, contract; hits emit no metrics line, failures store nothing). Keys are **scoped to the gate's own inputs** where its verdict cannot depend on the rest of the tree — pass the input globs to `gate_cache_key`, and omit them only for a gate that genuinely reads everything. `.gate-cache/.last-stop` holds the Stop-level short-circuit (`pass:<tree>` / `blocked:<tree>`). The wiring gate bypasses the cache in final mode (`WIRING_FINAL=1`) — a normal-mode pass with open IOUs must not satisfy the final-mode run that blocks on them. `GATE_CACHE_DISABLE=1` forces every run to do real work.
- **Commit gates.** `precommit-gates.sh` (header: scope rule, escape hatches) runs the three code gates on the **staged** change set from the `pre-commit` hook. They moved off Stop because a reactor build per conversational turn made interactive work unusable; enforcement is unchanged, only its boundary moved. Two refusals guard the boundary itself: **merge commits are never gated** (the staged set is the other side's whole delta, gated when it first landed), and a gated staged file whose **worktree copy differs from the staged copy blocks with a re-stage instruction** — the gates can only judge worktree content, and the verdict must be about the bytes being committed. Skip one commit with `AFK_SKIP_PRECOMMIT_GATES=1` or `git commit --no-verify`. Each of the three is still runnable standalone (scope = working tree) for a manual check.
- **Agent-only, on every surface.** The `pre-commit` hook is installed in the *shared* hooks dir, so it fires in every worktree and in the main checkout — but like `branch-name-gate.sh` it returns immediately unless an agent runtime marks the environment (`afk_agent_session`, `lib/provider.sh`). A human's terminal/IDE commit is never gated: gating exists to hold an *unattended* agent to the bar, and a human is already reading their own diff.
- **Commit-path wall clock.** An agent commits through a tool call with its own timeout, so a commit-time gate that outlives it kills the commit. Two bounds keep that from happening: the maven-lock wait drops to `AFK_MAVEN_LOCK_WAIT` (240s on this path, 900s for a manual run) instead of parking behind a sibling worktree's reactor, and the skills that commit code (`/afk:execute` Step 6, `/afk:bug`'s fixer, `/afk:settle-mr`'s round commits) invoke `git commit` with an explicit long tool timeout. A gate timing out allows the commit — blocking it because another build holds the lock helps nobody.
- Wiring gate: verdict model, IOU ledger grammar (`.claude/wiring-ious.md`), and the `/verify-seams` judgment boundary: script header; skip heuristics (framework-wired annotations, convention-consumed filenames, token rules) commented at each check in the body.
- Maven-invoking gates serialize via `maven-lock.sh` — rationale, lock path/staleness, and the `acquire_maven_lock`/`release_maven_lock` wrap contract for any new gate's mvnw call: its header.
- Maven invocations are reactor-based with `--also-make` — never trust `~/.m2` for sibling modules; stale jars cause APT `Expected a DeclaredType, got <error>` false failures. Cross-**worktree** local-repo races are designed out one level up: worktrees provisioned by `skills/afk/bug/scripts/create-worktree` carry a private `.mvn/maven.config` (`-Dmaven.repo.local=<worktree>/.m2/repository`, seeded minus `*-SNAPSHOT`), which every `./mvnw` a gate runs inherits automatically — the maven-lock above still serializes reactors *within* one checkout.
- `lesson-append.sh` / `lesson-digest.sh`: usage, always-exit-0 best-effort contract, `LESSON_LEDGER_DISABLE=1` / `LESSON_LEDGER_FILE`: script headers; grammar: `skills/afk/lessons/LEDGER-FORMAT.md`.
- `mutation-probe.sh`: exit 0 = mutation signal printed; exit 3 = `unavailable`/timeout — callers treat it as "no signal", never a failure. Usage, `PITEST_VERSION` / `MUTATION_TIMEOUT`, the per-service `pitest-junit5-plugin` enablement snippet: script header. The review gate's test-veracity skill owns the sampling rule.
- `app-start-gate.sh [leaf-module]` (default `11700-payable/payable`), run from the repo root: `bash tools/payable/ai-agents/plugins/workflow/hooks/app-start-gate.sh`. Exit codes: 0 started, 2 code failure (incl. a UI build failure or a build leaving no `public/index.html`), 3 environment failure (not a code bug), 4 timeout. Env vars — semantics in the script header: `APP_START_TIMEOUT`, `APP_START_PORT`, `APP_START_KEEP`, `APP_START_SKIP_UI` (why it is NOT Maven `-DskipUi=false`: the "UI pass" comment in the script body), `CI_PROJECT_DIR`, `APP_START_REUSE`. Kept fixed-port instance state + self-cleanup: header.
- Java format fix: the gate prints the exact `formatter-maven-plugin:format` command scoped to the failing files. Formatter config is the repo-root `eclipse-code-formatter.xml`.
- **Latency metrics & budget.** Every gate run doing real work (scope-check no-ops excluded) appends one JSONL line to `.claude/metrics/gate-latency.jsonl` **in the gated repo** via `gate-metrics.sh`: `ts`, `gate`, `result` (`pass`/`blocked`, or `ok`/`code_failure`/`env_failure`/`timeout` for app-start), `duration_ms`, plus gate-specific fields (`lock_wait_ms` = maven-lock serialization tax, `package_ms`, `detail`). `stop-gates.sh` also emits a `context` line (the shared derivation, with `changed`), so the per-Stop floor is visible rather than hidden inside the first gate that happens to run. Summarize with `bash tools/payable/ai-agents/plugins/workflow/hooks/gate-metrics-report.sh` (per gate: runs, red count, p50/p95/max).
  Budget: p95 should stay within the **Typical cost** column above — a sustained breach triggers optimization, never optimize a gate without this data. Read the numbers with the cost model in mind: a breach is nearly always a spawn count (a loop that forks per file, per line, or per token), so **count subprocesses before tuning anything else**. Only after that: compile gate `lock_wait_ms` share, then `mvnd`/offline `-o`; app-start `package_ms` vs boot time, `APP_START_SKIP_UI`. Emit-before-work is required — call `gate_metrics_begin` before the gate's first real command, or the measurement understates what the human waits for. `GATE_METRICS_DISABLE=1` silences emission; emission failures never fail a gate.
- **Host-level latency.** The spawn cost above is a property of the machine, not the gates. On Windows it is dominated by realtime AV scanning of MSYS process creation: Defender exclusions for the Git install dir, the checkout tree, and `.m2`, plus process exclusions for `bash.exe`/`git.exe`, move it by roughly an order of magnitude and need no plugin change. Worth checking before attributing slowness to a gate.
- `skill-registry-gate.sh`: the three checks (incl. the env-toggle E-table), ambient-var whitelist, and the mechanical-vs-`/afk:setup audit` boundary: script header. Add a skill dir → same commit adds it to `plugin.json`'s `skills` array **and** a `/afk:<name>` mention to the plugin's `CLAUDE.md` + `README.md`, or this gate blocks the next Stop.
- UI lint: nearest-ancestor `.eslintrc.*` = lint workspace, silent-allow rules: script header; the `eslint` binary resolves from the hoisted root `node_modules` via `npx --no-install`.
