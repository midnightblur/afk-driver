# Harness gates

Deterministic quality gates shipped with the afk-toolkit plugin. All gates run against the working tree's Git root (`git rev-parse --show-toplevel`); a build gate no-ops unless the repository selects its kind in `build-gates` and the kind's own key resolves (no `maven.reactor-pom` on disk ⇒ silent allow).

**Where each gate fires.** Three surfaces, wired differently:

- **Stop** — one hooks.json entry, `stop-gates.sh`, which runs the five cheap gates (wiring, skill-registry, native-contract, genericity, behavior-registry) in a single process. The adopted harness Stop gates (`java-rules-gate.sh`, `i18n-parity-gate.sh`) stay separate entries because they live in another tree.
- **Commit** — `precommit-gates.sh` runs native-contract plus the expensive code gates from the `pre-commit` git hook that `install-git-hooks.sh` installs, for **agent-driven commits only**. WHICH code gates run is the repository's `build-gates:` list: each selected build-gate adapter reports the gates its change set needs (`ADAPTERS.md`).
- **PreToolUse / on demand** — `protected-branch-guard.py` (with its lavish rule), the adopted guards, `adapters/build-gate/maven/app-start-gate.sh`, `adapters/build-gate/maven/mutation-probe.sh`.

**A Stop block is a decision, not an exit code.** Gate findings are collected
by `stop-gates.sh` and emitted once through `afk_block_stop` (`hooks/lib/provider.sh`):
the text goes to stderr and to a `{"decision":"block","reason":…}` object on
stdout, and the exit code comes from the active adapter. A harness that reads
only one of those channels records a bare `exit 2` as a failed hook and lets the
turn finish. The two adopted harness Stop gates use the same emitter.

**Every hook entry goes through one launcher.** `hooks.json` commands are
`afk-python "${CLAUDE_PLUGIN_ROOT}/hooks/run-hook.py" plugin|repo <handler.sh> [args]`
(`--soft` before the kind pins the exit code to 0 for an advisory handler; `--deadline <seconds>` sets the launcher's own budget, see below). A
command string is parsed by whichever shell the harness picked — a POSIX shell
on one, PowerShell on another — so it must carry no shell syntax; and a bare
`bash` on Windows resolves to the WSL stub in the system directory, which cannot
run these handlers. The launcher takes both problems: it locates a real Git Bash
(`AFK_BASH`, `GIT_BASH`, a lookup relative to `git --exec-path`, the known
install locations, then `PATH` minus the system directory), resolves the handler
under the plugin or the checkout, forwards stdin and the exit code, and exits 0
on an absent handler. Add a hook: add the entry in that shape — never a second
launch mechanism.

**Two bails come before any shell.** `repo-list <event>` exits 0 when the
repository manifest declares no entry for the event. A plugin handler its
provider declaration makes a no-op exits 0: `run-hook.py` `POLICY_NOOP` reads
`hooks/lib/providers/<name>.json` through `hooks/lib/provider_facts.py`, the same
keys `afk_provider_fact` gives the shell. Past the bails, the launcher runs a
handler only when `AFK_PYTHON` names its own interpreter: anything else is a
missing or stale setup, so it fails like a missing shell and names `/afk:setup`.

**The launcher owns the process tree and the clock.** Every entry carries an explicit `timeout` T and a `--deadline` D below it: `D = floor(min(0.95·T, T − 1))`. The harness kills a hook at T without waiting for a verdict, and on Windows that kill leaves the handler's children running. D fires first. Past D the launcher ends the handler's whole process tree and answers itself: a plugin handler gets one stderr line (`verdict unknown`) and exit 0, never a block; a repository handler fails closed as before, with each entry capped to the budget left. On Windows each handler runs in its own Job Object (kill-on-close, no breakaway) nested in a job for the launcher, so killing the launcher also ends the tree; on POSIX each handler is a session leader and the launcher signals its group. `worktree-remove.sh` is the one exception on Windows: it starts a deliberately detached waiter, so it runs with no job and a deadline walks its parent chain. Stop does not wait on a survivor: a killed scan is an unknown verdict. `hooks/native-contract-gate.sh` check M refuses an entry without `timeout` or `--deadline`, or with D at or above the bound; an entry outside the launcher needs a `hook-deadline` line in `hooks/native-contract-allow.txt` naming its own deadline.

**Cost model — spawns × bytes × patterns × output.** On Windows/git-bash a spawn costs ~0.5–2s (MSYS fork emulation) against ~20–40ms for a native Windows spawn, and degrades under load. A repository-wide scan costs more than its spawns: `git grep -F` matches each pattern in a separate pass, and `-o` repeats every pattern per printed match, so time grows with files × patterns × matches. Two measured cases on a 52,852-file tree: `git grep -o` with 50 mixed tokens took 44s and with 200 took over 630s, while `git grep -l` with 200 tokens took 8.7s. The rules below follow from both costs:

- **Narrow the universe first.** Search the files the change touched before the tree, and send the tree only the questions still open.
- **Route every repository-wide content scan through `hooks/lib/bounded_scan.py`.** It runs under a deadline (`AFK_SCAN_DEADLINE`, default 120s) and a repository lock, lists matching files with `-l` instead of printing matches, and returns an answer sized by the candidates. Check M of `native-contract-gate.sh` refuses any other scan in a Stop-path gate source.
- **A scan that fails, times out, or finds the lock held is verdict unknown, never a block.** A gate returns rc 3; `stop-gates.sh` neither blocks nor stamps all-green, and the metrics line records `unknown`.

- The change set is derived **once per Stop** (`gate-context.sh`) and shared; no gate runs `git status` or hashes a file itself. Scope tests (`gate_ctx_filter` / `gate_ctx_any`) are bash pattern matches, so "no `.java` changed" costs nothing.
- A gate is **entered only when the change set holds a path it could gate** (scope-driven dispatch in `stop-gates.sh`). A gate that judges the *branch* rather than the worktree (registry vs disk, native contract, added prose) is dispatched on the working-tree list **plus** the committed list (`gate_ctx_branch`) — testing only the worktree stops gating a change at the moment it is committed, which is when it matters most.
- A tree identical to the last **all-green** Stop skips every gate (`.last-stop` in the pass-cache directory). A blocked verdict never short-circuits: the suite runs again on every Stop. An unchanged tree blocks at most 3 Stops in a row in one session (the payload's `session_id`), so an agent that makes no change cannot loop on these gates until a run cap; a repository's own Stop handlers (`.afk/hooks.json`) are outside this bound. Later Stops in that session on that tree are allowed with a notice on stderr and in `systemMessage` that names the blocking gates. No all-green stamp is written, and any change to the tree resets the count. A gate that **crashes** (any exit but 0/2, or a failed source) never blocks, but that Stop records no all-green stamp — the next turn re-runs the suite instead of inheriting a green it didn't earn.
- Per-gate pass caches are keyed on **that gate's own inputs** (`gate_cache_key <gate> <glob>…`), so editing a spec file does not re-run the plugin-registry gates.
- New loops must not spawn per file or per line. Batch instead: one bounded scan for all tokens (`bounded_scan.py`), one `git hash-object --stdin-paths` for all files, one `awk` pass over a stream. A per-item probe that must read the file (an annotation check, a ledger lookup) belongs **after** the batched pass, where it sees only the few items the batch could not clear — and a ledger or lookup table is read once into a variable, never grepped per item.
- Watch the loop shape too, not just the spawns: a `while read … <<<"$blob"` nested inside a per-candidate loop re-materialises the here-string every iteration. Fold the blob into an associative array in one pass and look up. On a branch carrying 150 new files that alone was 29s of the wiring gate's 52.

**Repository-owned gates.** A repository can ship gates of its own — a security
guard, a language rule set, a translation check — and this plugin runs them
without knowing what they are. It declares them in `.afk/hooks.json`
(`CONFIG.md` "Repository hooks"): one entry per handler with its `event`,
`matcher`, `timeout` and repository-relative `script`. `hooks.json` invokes
`run-hook.py repo-list <event>` once per event; the launcher resolves each
script under the working tree's Git root (the root every plugin gate uses),
refuses one that resolves outside it, and exits 0 when the manifest is
absent — so the plugin stays inert in a repository that declares none. A handler a repository DOES declare and this checkout cannot run
— missing script, unusable matcher, unparsable manifest, no verdict inside its
timeout — is a configuration error, not a skip: on Stop and PreToolUse the
launcher blocks with the decision object a failed gate emits, naming each
entry, so a required gate cannot disappear by being misdeclared. On the other
events it says so on stderr. They are deliberately NOT resolved under the
plugin root: a repository's gates must track the checkout, not the installed
plugin. Their escape hatch is the repository's own.

A repository handler's leftover processes end when the handler exits, on every OS: the launcher ends the handler's process tree (a Job Object on Windows, a process group on POSIX). Only plugin handlers in `DETACHES_HELPERS` (`hooks/run-hook.py`) are exempt. A repository hook that needs a lasting background process must detach it itself, outside the launcher's tree, or not use a hook for it.

`.afk/hooks.json` carries only hooks specific to that repository. A check that
applies to every repository ships as a plugin hook (the table below), not in
`.afk/hooks.json`.

Rules:

- **`branch-name-gate.sh` is a git hook, not an agent-harness hook** — not wired into `hooks.json`; it runs inside git itself on ref updates, which is what catches *every* creation path an agent uses, no shell-command parsing. Enforcement scope (agent-only markers, creation-only, remote-DWIM allowance) and escape hatches (`AFK_SKIP_BRANCH_CHECK=1`, `git config afk.branchNameGate false`, removal): script header. Installation (`SessionStart` runs `install-git-hooks.sh --quiet`, so enabling the plugin is the whole opt-in; idempotent / self-scoping / worktree-safe / non-destructive; fallbacks: `/afk:setup` register H5 or a manual run): `install-git-hooks.sh` header. That installer now places **two** hooks — `reference-transaction` (branch names) and `pre-commit` (the code gates); both follow the same never-clobber rule.
- **`git-backstop.py` — protected-branch backstop, called by both installed hooks.** `precommit-gates.sh` (commit) and `branch-name-gate.sh` (`reference-transaction`, `prepared` phase) run it first, agent-only, before their own escape hatches. Commit: refused in the main checkout on any branch and on a protected branch of a linked worktree. Ref transaction: a `git pull --ff-only` the guard authorized passes (record consumed at `committed` or `aborted`; ADR-0011); refused for the main checkout's own `HEAD` and the branch it has checked out (a `git worktree add` in flight, which shows as a `worktrees/*/HEAD.lock` under 10 s old, passes), and for a linked worktree's own protected branch, a rebase target included; an update to the same value passes. Python starts only for a `HEAD` or `refs/heads/*` line. Exit 3 refuses and any other failure warns and lets git continue; the code gates in `precommit-gates.sh` run only where `.afk/` exists. Bypass: `AFK_ALLOW_PROTECTED=1`, or `AFK_WORKTREE_OP=1` (exported by the plugin's own worktree scripts). A vetoed `checkout` leaves the index switched and a vetoed `rebase` in progress. Internal faults, an import error included, warn and allow.
- **Worktree cleanup handlers.** `worktree-remove.sh` (the harness's worktree-removal event, or its session-end event; path = `worktree_path` else `cwd`) and `worktree-prune.sh` (`SessionStart`, one `stat` when the repository has no plugin-made worktree) call `scripts/remove-worktree.py`. Only a worktree with an owner record is touched; one with uncommitted or unpushed work, a copied personal file changed since the copy, an ignored file the copy step or build-gate provisioning did not record unchanged (only the build-output and cache folders in `scripts/worktree_owner.py` `DISPOSABLE_DIRS` and `DISPOSABLE_ROOTS` go unread), another live or unknown owner, or a git state it could not read inside the hook's `--deadline` is kept and the resume/remove commands are printed. Neither handler passes `--force`. A session ending inside its own worktree starts a detached `--after-exit` waiter that assesses it once the harness process is gone. Handlers never fail the harness.
- **`protected-branch-guard.py` — PreToolUse guard, agent-only.** One manifest entry per harness, the last `PreToolUse` group. It runs under `afk-python` directly (no shell) and reads the provider declarations in `hooks/lib/providers/<name>.json`. It judges the resource a call mutates (the main checkout, a protected branch's worktree, a worktree another live session holds) and allows everything else, composed commands and unknown programs included (ADR-0010). It snapshots guarded checkouts before an allowed shell call. It fails closed inside a work tree (20 s deadline, under the 30 s hook timeout). Placement comes from the file layout; one `git rev-parse` covers unusual layouts. Protection comes from `scripts/protected-lookup.py`, which reuses a forge answer for at most 5 minutes (`AFK_PROTECTION_CACHE_TTL`; never for the default branch, `main` or `master`). A refusal is exit 0 plus the deny JSON, never exit 2: the H-2 harness runs the command when a hook exits 2. Bypass: `AFK_ALLOW_PROTECTED=1` set by a human at launch. The same process runs the **lavish rule** (`lib/lavish_direct.py`) first: a shell call that runs `lavish-axi` in executable position (bare, by path or `.cmd`/`.ps1` shim, behind `env`/`command`/`exec`/`npx`, or inside `bash -c`/`pwsh -Command` or a double-quoted `$(…)`) or sets `LAVISH_AXI_HOST` is denied with the `scripts/lavish_show.py` command; searches, mentions, comments, `declare -p`, `lavish-axi --version` and unreadable shell syntax pass, and `AFK_ALLOW_PROTECTED=1` does not lift it (`LAVISH.md` "Pin and invocation"). Rule: `SAFETY.md` "Worktree per session".
- **`protected-branch-meter.py` — PostToolUse change meter.** Compares the snapshot with the checkout after the call, injects the changed paths and the recovery, and writes the quarantine the guard enforces. Never blocks, exits 0 on any fault (ADR-0012).
- **`protected-branch-occupancy.py` — SessionStart advisory.** Registers the session in its linked worktree and prints one line when another live session outside its group holds it. Never blocks (ADR-0013).
- **Caveat — agent-launched IDE/terminal.** The marker propagates to child processes, so if an agent launches IntelliJ or a shell (e.g. `scripts/create-worktree` with the IDE launch left on), branch creation *within that launched process* inherits the agent marker and is still gated. A terminal/IDE you started yourself is unaffected. Use the bypass or config-disable in the rare launched-process case.

- **Worktree provisioning is adapter-owned.** `scripts/create-worktree` and `scripts/worktree-provision` carry no build command: they copy what `worktree.copy` names and hand the worktree to each selected build gate's `worktree-provision` verb. `genericity-gate.sh`'s check 0 enforces that. Smoke tests: `bash scripts/tests/create-worktree-smoke.sh` and `bash scripts/tests/worktree-provision-smoke.sh` (both run in a disposable temp repository with stub build tools — never a real checkout).

- Escape hatch for all Stop gates: create `.claude/hooks/.gate-disabled` **in the repo being gated** (leave a reason inside; delete to re-enable).
- **Provider shim.** `hooks/lib/provider.sh` is the adapter registry — detection order, plugin root/data paths, envelope parsing, decision emission, block contract: its header. One adapter per supported harness under `hooks/lib/providers/<id>.sh`, each with a registry row in `PROVIDERS.md` and envelope fixtures under `hooks/tests/envelopes/<id>/`. Hooks source the registry and call the `afk_*` functions; gate logic stays provider-free. Smoke tests: `bash "$AFK_PLUGIN_ROOT/hooks/tests/hook-smoke.sh"` (every envelope-consuming hook under every adapter; fails without jq). Latency: `afk-python hooks/tests/bench-hooks.py` times every registered command per event (p50/p95; `--budgets` checks the launcher bails against `BUDGET_MS`, informational in CI; usage: its header).
- **Shared context.** `gate-context.sh` derives the change set once per Stop (`AFK_CTX_CHANGED` / `_NEW` / `_LIVE` / `_HASHES` / `_TREE`) and every gate reads it — contract, variables (deliberately unexported — the lists are unbounded and would ride every native child's environment), and the fork budget in its header. The tree digest also folds in the wiring IOU ledger directly, so editing `.claude/wiring-ious.md` busts the short-circuit and wiring's cache however the change set was scoped. `gate_ctx_build_staged` is the commit-time variant (scope = staged paths, content = working tree). Merge-base (`gate_ctx_mergebase`) and the committed-change list (`gate_ctx_branch` → `AFK_CTX_BRANCH`) are lazy, so a turn that short-circuits pays for neither. `AFK_GATE_CTX_DISABLE=1` forces a rebuild per call.
- **Pass cache.** Gates remember their last **pass** under the gated worktree's own git directory, `$(git rev-parse --git-path afk/gate-cache)` — never in the working tree, and one cache per linked worktree (`gate-cache.sh` header: key shape, contract; hits emit no metrics line, failures store nothing). Keys are **scoped to the gate's own inputs** where its verdict cannot depend on the rest of the tree — pass the input globs to `gate_cache_key`, and omit them only for a gate that genuinely reads everything. `.last-stop` in the same directory holds the Stop-level short-circuit (`pass:<tree>` / `blocked:<count>:<session>:<tree>`, where count is the session's consecutive blocked Stops on that tree). The wiring gate bypasses the cache in final mode (`WIRING_FINAL=1`) — a normal-mode pass with open IOUs must not satisfy the final-mode run that blocks on them. `GATE_CACHE_DISABLE=1` forces every run to do real work.
- **Commit gates.** `precommit-gates.sh` (header: scope rule, escape hatches) runs the comment gate, the scoped native-contract gate, then the code gates (format and lint before compile) on the **staged** change set from the `pre-commit` hook; the first block stops the run. The expensive code gates moved off Stop because a reactor build per conversational turn made interactive work unusable; native-contract runs at both boundaries. Two refusals guard the code boundary itself: **merge commits are never gated** (the staged set is the other side's whole delta, gated when it first landed), and a gated staged code file whose **worktree copy differs from the staged copy blocks with a re-stage instruction** — the code gates can only judge worktree content, and the verdict must be about the bytes being committed. Skip one commit with `AFK_SKIP_PRECOMMIT_GATES=1` or `git commit --no-verify`. Every gate is still runnable standalone (scope = working tree) for a manual check.
- **Agent-only, on every surface.** The `pre-commit` hook is installed in the *shared* hooks dir, so it fires in every worktree and in the main checkout — but like `branch-name-gate.sh` it returns immediately unless an agent runtime marks the environment (`afk_agent_session`, `lib/provider.sh`). A human's terminal/IDE commit is never gated: gating exists to hold an *unattended* agent to the bar, and a human is already reading their own diff.
- **Commit-path wall clock.** An agent commits through a tool call with its own timeout, so a commit-time gate that outlives it kills the commit. Two bounds keep that from happening: the maven-lock wait drops to `AFK_MAVEN_LOCK_WAIT` (240s on this path, 900s for a manual run) instead of parking behind a sibling worktree's reactor, and the skills that commit code (`/afk:execute` Step 6, `/afk:bug`'s fixer, `/afk:settle-change`'s round commits) invoke `git commit` with an explicit long tool timeout. A gate timing out allows the commit — blocking it because another build holds the lock helps nobody.

- **Latency metrics & budget.** Every gate run doing real work (scope-check no-ops excluded) appends one JSONL line to `$(git rev-parse --git-common-dir)/afk/metrics/gate-latency.jsonl` — one file shared by every worktree of the gated repo, never in the working tree; `GATE_METRICS_FILE` overrides — via `gate-metrics.sh`: `ts`, `gate`, `result` (`pass`/`blocked`/`unknown` — the gate could not reach a verdict, for example a scan that timed out — or `ok`/`code_failure`/`env_failure`/`timeout` for app-start), `duration_ms`, plus gate-specific fields (`lock_wait_ms` = maven-lock serialization tax, `package_ms`, `detail`). `stop-gates.sh` also emits a `context` line (the shared derivation, with `changed`), so the per-Stop floor is visible rather than hidden inside the first gate that happens to run. Summarize with `bash "$AFK_PLUGIN_ROOT/hooks/gate-metrics-report.sh"` (per gate: runs, red count, unknown count, p50/p95/max).
  Budget: p95 should stay within the **Typical cost** column above — a sustained breach triggers optimization, never optimize a gate without this data. Read the numbers with the cost model in mind: a breach is a spawn count (a loop that forks per file, per line, or per token) or a scan whose bytes × patterns × output grew, so **count subprocesses, then measure each repository-wide scan, before tuning anything else**. Only after that: compile gate `lock_wait_ms` share, then `mvnd`/offline `-o`; app-start `package_ms` vs boot time, `APP_START_SKIP_UI`. Emit-before-work is required — call `gate_metrics_begin` before the gate's first real command, or the measurement understates what the human waits for. `GATE_METRICS_DISABLE=1` silences emission; emission failures never fail a gate.
- **Host-level latency.** The spawn cost above is a property of the machine, not the gates. On Windows it is dominated by realtime AV scanning of MSYS process creation: Defender exclusions for the Git install dir, the checkout tree, and `.m2`, plus process exclusions for `bash.exe`/`git.exe`, move it by roughly an order of magnitude and need no plugin change. Worth checking before attributing slowness to a gate.
