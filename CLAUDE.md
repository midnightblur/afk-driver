# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This repo is the **`afk` Claude Code plugin** — a chain of skills inspired by and built upon [Matt Pocock's AFK workflow and skills](https://github.com/mattpocock/skills), adapted to Nakisa's Jira + GitLab + Maven monorepo. **AFK = "away from keyboard":** the upstream idea was to spend focused effort up front on requirements + design, then let agents implement the whole thing autonomously with no human in the loop. **That fully-autonomous vision is not realized here** — what this repo delivers is a structured, **human-in-the-loop** workflow whose implementation phase is *somewhat* automated but still human-gated. The "AFK" name is kept for continuity with the upstream inspiration; it does **not** describe how this repo works today. Accordingly there is **no autonomous driver**: every stage is run interactively by a human in a Claude Code session. The chain takes a feature from raw idea → grilled requirements → PRD → (optionally) **an interactively-crafted UI mockup** (`/afk:prototype`) → architecture → SDD → (optionally) **grilled verification scenarios** (`/afk:grill-verification` interviews → `/afk:to-verification-plan` writes `VERIFICATION-PLAN.md`: UI journeys + API scenarios) → a **local execution plan** (a `plan/` dir of subtask contracts, not Jira issues) → execution → an **optional feature smoke gate** (`/afk:smoke-test`). You invoke each stage yourself, including `/afk:execute`, which you run once per subtask in a session on the parent ticket's branch.

The repo contains only the skills — workflow skills under `skills/afk/<name>/SKILL.md`, plus general-purpose utility skills (not part of the AFK chain) under `skills/utils/<name>/SKILL.md` — and the plugin manifests. The *work* the chain drives is Java/Maven inside a sibling core-services checkout. Jira (`mcp__jira__*`) is the tracker **only for the parent Enhancement/Bug** — `/afk:to-ticket` publishes the PRD there and `/afk:to-sdd` splices an SDD pointer; the subtask plan and its progress live entirely on disk. GitLab (`glab`) is the SCM.

There is no Python package, no test suite, and no build step — editing a `SKILL.md` and running `/reload-plugins` is the entire dev loop.

## Plugin layout & install

The plugin lives at `.claude-plugin/plugin.json` (manifest) + `.claude-plugin/marketplace.json` (local marketplace) + `skills/afk/<name>/SKILL.md` (AFK-chain skills) and `skills/utils/<name>/SKILL.md` (standalone utilities) — both dirs are declared in the manifest's `skills` array (which replaces the default `skills/` scan because the marketplace `source` resolves to the repo root). Install once via `/plugin marketplace add <repo>` + `/plugin install afk@afk-marketplace`, then persist via `enabledPlugins` in `~/.claude/settings.json`. After editing any `SKILL.md`, run `/reload-plugins` to pick up changes without restarting. See `README.md` for the full install snippet.

## The skills

- **Mandatory chain**: `/afk:to-prd` → `/afk:to-ticket` → `/afk:to-subtasks` → `/afk:execute`. `/afk:to-ticket` is the one step that publishes the local PRD to the parent Enhancement (the only design-chain skill that writes to the tracker). `/afk:to-subtasks` emits a **local plan** (`plan/PLAN.md` index + `plan/NNNN-slug.md` per subtask) — no Jira. You run `/afk:execute` yourself, once per subtask, and it advances that subtask's row in the local progress tracker.
- **Optional design layer**: `/afk:grill-requirements` (raw-idea grilling; maintains `GLOSSARY.md` only — no decision records) → `/afk:to-prd` (PRD + requirement ADRs under `.../adr/requirements/`; **local artifacts only — does not touch the tracker**) → (optionally) `/afk:prototype` (an **interactive UI-crafting loop**, not a grill and not a one-shot producer: reads the PRD User Stories, anchors to the **real frontend's** components + tokens, writes self-contained HTML the user opens and refreshes, and reshapes it live as the conversation goes; self-gates `no_ui` for backend/API/refactor features; durable-lite output — the won direction is `PROTOTYPE.md` + chosen HTML sibling to the PRD, traceable to User Stories so `/afk:grill-verification`'s UI journeys trace to it, losing scaffolding discarded; **local-first**, with a **frictionless opt-in** push to a persistent, team-shareable `claude.ai/design` project that is a share mirror only — the in-repo `PROTOTYPE.md` stays canonical) → `/afk:grill-solution` (top-down L1→L8 interview) → `/afk:to-sdd` (writes `SDD.md` + per-decision design ADRs under `.../adr/design/` sibling to the PRD; owns the `## SDD` section of the parent Enhancement description) → `/afk:to-design-brief` (optional digest: synthesizes PRD + SDD + ADRs into a 1-2 page `DESIGN-BRIEF.md` for stakeholder review and pre-SDD reading; **repo-only — does not touch the tracker**, shared with stakeholders out of band). Recommended for new complex features; skip for small bugs / refactors / tooling.
- **Optional verification design**: `/afk:grill-verification` (interview) → `/afk:to-verification-plan` (synthesis). `/afk:grill-verification` interviews the user to design the feature's verification scenarios across **two modalities** — it writes **no file** (a grill, like `/afk:grill-requirements` and `/afk:grill-solution`); `/afk:to-verification-plan` then synthesizes the settled scenarios into `VERIFICATION-PLAN.md` sibling to the PRD: **UI journeys** (the real browser flows that decide "this feature works", traced to PRD User Stories) and **API scenarios** (direct-REST checks proving the backend contract for API/MCP callers who bypass the UI, traced to SDD §3 endpoints). Walking them concretely routinely surfaces PRD/SDD gaps. **UI journeys** can be designed after `/afk:to-prd`; **API scenarios need the SDD's §3 endpoint contracts**, so a pre-SDD run designs UI journeys only and defers the API section — re-run both skills after `/afk:to-sdd` to add it (`/afk:to-verification-plan` **appends**, preserving the UI section). **Local-only — no tracker.** Its plan is what makes `/afk:to-subtasks` emit the smoke gate + a build subtask per modality. The how-to-build-the-tests recipes are **not maintained in this repo** — they live canonically in the payable repo at `11700-payable/verification/ui-e2e/AUTHORING.md` and `11700-payable/verification/api/AUTHORING.md` (versioned with the verification code so they can't drift); every AFK skill only **points** at them by path, never embeds a copy.
- **Optional feature gate**: `/afk:smoke-test` — the **feature-level** completion gate (distinct from `/afk:execute`'s per-subtask `api` / `e2e/browser` tiers). It **only executes** already-built scenarios — it authors nothing. Present only when a `VERIFICATION-PLAN.md` (from `/afk:grill-verification`) drove `/afk:to-subtasks` to emit a `## Feature smoke gate` in `PLAN.md` plus a terminal build subtask **per modality** — `NNNN-smoke-e2e` (UI journeys → `Scenario`s in the `11700-payable/verification/ui-e2e` Cucumber+Playwright catalog, per `…/ui-e2e/AUTHORING.md`) and `NNNN-smoke-api` (API scenarios → `node:test` `*.test.mjs` in `11700-payable/verification/api` using `../core`, per `…/api/AUTHORING.md`) — reviewed as code; env-limited scenarios like `@sap` / GL-post are tagged and excluded from the gate's green verdict. After **every** subtask is `done`, `/afk:smoke-test` runs both modalities (`npm run smoke` + `node --test`) against a **running app** and, only on green across both, stamps `Feature: complete` in `PLAN.md`. The same suites are reused by CI / scheduled / manual runs. It merges nothing and writes no Jira.
- **Tooling**: `/afk:tdd` (red-green-refactor doctrine, invoked from `/afk:execute` Step 5).

`/afk:to-subtasks` slices in **cited mode** when an SDD is present (each subtask references binding SDD sections + ADRs, lists the §9b seams it implements/uses, and carries a Conflict procedure block) and in **uncited mode** otherwise (PRD-only; human-gated per ticket). Mode is set by what's upstream: PRD + SDD (from `/afk:grill-solution`) → cited; PRD only (from `/afk:grill-requirements`) → uncited.

## Lockstep: the subtask plan contract

The plan is the load-bearing interface between `/afk:to-subtasks` (emitter) and `/afk:execute` (parser + progress writer). It is entirely on disk: `plan/PLAN.md` (the index — solution map, seam register, progress tracker) + one `plan/NNNN-slug.md` contract per subtask, sibling to `PRD.md`/`SDD.md`. A subtask's **id** is its filename stem (`NNNN-slug`); there are no Jira keys in the plan. If you add, rename, or change a section, update **both** `skills/afk/to-subtasks/SKILL.md` (the "Subtask contract" emitter) and `skills/afk/execute/SKILL.md` (Step 1 parser) in the same commit — they live in the same repo specifically so this lockstep is enforced by a single commit. Likewise the outcome status set: if you broaden it, update the status list in `/afk:execute` Step 12 and any skill that references it.

The contract's base sections: `## Goal / Scope / Acceptance / Verification / Parent PRD / Blocked by / Implementation Notes`. `## Verification` is a **tiered table** (static → unit → integration → api → e2e/browser, where `api` is a direct-REST endpoint check via `11700-payable/verification/api` + `../core`); the implementor must turn every declared tier green. Cited mode adds six: `## Design refs / Seams / Produces / Parent SDD / Consumes / Conflict procedure`.

`/afk:execute` owns the PLAN.md progress tracker's `Status` column (`pending` → `designing` → `developing` → `verifying` → `done`, or `blocked(<reason>)`) — one cell per run — plus each subtask file's `## Implementation Notes` block. Everything else in the plan is the human's.

## Cited-mode contract

The contract is enforced at three checkpoints — drift is impossible to ship without surfacing somewhere:

1. **Slicing time (`/afk:to-subtasks` Validation).** Checks (a)–(d):
   - **Graph validation (a)** — every `## Consumes` line resolves to a `## Produces` bullet on a subtask earlier in rank order. Forward refs / orphan consumers / multi-producer collisions all bounce.
   - **Anchor quality (b)** — every `## Produces` `{grep-anchor}` is checked against (i) a forbidden-generic-token list (`class`, `interface`, `void`, `function`, `def`, `method`, `struct`, `enum`, `type`, `record`); (ii) length ≥12 chars; (iii) trial `ctx_search` against `{file}` at HEAD must return ≤1 match. Ambiguous anchors that would fail-open at runtime are rejected at declaration time.
   - **Acceptance citations (c)** + **seam coverage (d)** — every cited Acceptance bullet ends with a resolving citation tag; every SDD §9b seam appears in the seam register with a named implementer that lists it `implement:` and carries its seam-test as a `## Verification` row.
2. **Consumer preflight (`/afk:execute` Step 2).** Reads `## Design refs` and `## Parent SDD` to load binding SDD/ADR context. Then for each `## Consumes` line `{PRODUCER-ID} {file}#{grep-anchor}`, reads `{file}` and greps for `{grep-anchor}`. A miss exits `contract_mismatch` carrying the producer id (no retry; record on both consumer and producer subtask files + set both tracker rows `blocked`). A binding-decision break exits `design_conflict` (no retry; routes to `/afk:grill-solution`).
3. **Producer self-preflight (`/afk:execute` Step 9).** Right before declaring `success`, the subtask greps each of its own `## Produces` anchors on the branch. A miss exits `produces_drift` (no retry; route the human to fix the impl OR re-emit the slice). Without this step, signature drift would surface only at the next consumer's preflight — surfacing the failure on the wrong subtask.

`## Produces` is mandatory on every cited subtask, even leaves with no consumer — it doubles as the reviewer's cheat-sheet, the producer-self-preflight grep target, the `static`-tier grep target, AND the next subtask's consumer-preflight grep target.

## Section ownership invariants (don't violate)

- **Parent Enhancement description**: the PRD content is authored by `/afk:to-prd` (on disk) and published into the parent — as the full inlined body in native Jira formatting (ADF), inside an AFK-managed sentinel block — by `/afk:to-ticket`, which preserves all content outside that block. `## SDD` (when present) is owned by `/afk:to-sdd`. (The Design Brief is **not** published to the ticket — `/afk:to-design-brief` is repo-only.) Other prose belongs to the human. (Subtask progress is **no longer** spliced into the parent — it lives in the local `plan/PLAN.md` tracker.)
- **MR description**: the `<!-- afk:subtasks:start --> ... <!-- afk:subtasks:end -->` checklist block is auto-maintained by `/afk:execute`; everything outside is preserved verbatim.
- **The local plan (`plan/`)**: `/afk:execute` owns only the PLAN.md progress-tracker `Status` cell of the subtask it is running (+ the `Last updated` date) and that subtask file's `## Implementation Notes` block. **`/afk:smoke-test`** owns a disjoint slice of the same PLAN.md — the `## Feature smoke gate` table's `Status` cells, its `Last run` line, and the header `Feature:` line — and nothing else. The contract sections must round-trip losslessly. If you add a section, update both the `/afk:to-subtasks` emitter and the `/afk:execute` parser together (see Lockstep above); a section read by `/afk:smoke-test` (the gate) must be updated in lockstep with that skill too. The `## Feature smoke gate` is seeded from `VERIFICATION-PLAN.md` (written by `/afk:to-verification-plan` from a `/afk:grill-verification` interview, covering both UI journeys and API scenarios) and the build-subtasks' authoring recipes are the verification repo's `11700-payable/verification/{ui-e2e,api}/AUTHORING.md` (referenced, never copied) — change a gate field's shape and you touch all three (`to-verification-plan` emitter, `to-subtasks` seeder, `smoke-test` reader) in the same commit.

## Skill ↔ human ownership split (CR/Merge)

`/afk:execute` drives the progress-tracker status (`designing` → `developing` → `verifying` → `done`), the TDD loop, the verification tiers, commits, push, the MR checklist, and the subtask's Implementation Notes — then **stops**. It does NOT merge the MR. The human reviews the Draft MR and merges (and writes any gate fields) out of band. Auto-merging is outside the skill's lane — preserve this boundary when editing `/afk:execute`.

## Tracker boundary

`/afk:to-prd` produces **local artifacts only** (PRD.md + requirement ADRs on disk); it does not create or update any Jira/GitLab issue. Publishing the PRD to the tracker is the job of **`/afk:to-ticket`**: it publishes the **full PRD content** into an **existing** parent ticket's description as native Jira formatting (ADF — Jira Cloud), with any `mermaid` blocks rendered to PNGs **locally**, attached, and embedded inline as media nodes (the verified media-UUID method; no diagram source leaves the network). It is **idempotent** — the PRD lives in an AFK-managed sentinel block, so re-running updates in place and replaces prior `afk-fig*` attachments rather than duplicating; content **outside** the managed block (product-owner prose) is preserved verbatim unless the existing description is barebone. The intricate formatting/diagram/merge work is codified in `skills/afk/to-ticket/scripts/publish_prd.py` for deterministic behavior (it reads Jira creds from env or `~/.claude.json` and talks to the REST API directly, since attachment upload has no MCP tool). It deliberately **does not** create the parent (refuses without `parent_key`), sets **no label**, creates **no GitLab branch** (`/afk:execute` self-creates its branch), and publishes **PRD content only** — not the SDD/Design Brief. Only **`/afk:to-ticket`** (PRD body) and **`/afk:to-sdd`** (its `## SDD` pointer section) write to Jira; everything else stops at disk or GitLab. `/afk:to-prd`, `/afk:grill-verification`, `/afk:to-verification-plan`, `/afk:to-subtasks`, and `/afk:to-design-brief` are **local-only**; `/afk:prototype` is **local-first and tracker-free** — its canonical output (`PROTOTYPE.md` + chosen HTML) is on disk, and its **only** network egress is an **opt-in** `claude.ai/design` push (a share mirror, never Jira/GitLab/merge); `/afk:execute` touches **GitLab** (push + Draft MR) and the local plan, but **not Jira** — subtasks are local artifacts and their progress lives in `plan/PLAN.md`. `/afk:grill-verification` writes **nothing** (it only interviews); `/afk:to-verification-plan` writes only `VERIFICATION-PLAN.md` (+ gap notes) on disk. `/afk:smoke-test` is **local-only too**: it runs the verification suites (UI + API) against a target app and edits only its slice of `plan/PLAN.md` (the `## Feature smoke gate` Status cells + `Feature:` line) — no Jira, no GitLab push, no merge.

## Conventions to keep

- **Branch names** must match the GitLab regex `^[a-z0-9][a-z0-9/\-\.]*$` — the `mvu/afk/{enh_id_lower}` pattern is load-bearing for `/afk:execute`'s push.
- **Two ADR tiers, separate subfolders.** Requirement-level ADRs (what/why) live in `.../{TICKET-ID}/adr/requirements/NNNN-*.md` and are owned by `/afk:to-prd`. Design-level ADRs (how) live in `.../{TICKET-ID}/adr/design/NNNN-*.md` and are owned by `/afk:to-sdd`. Numbering is local to each subfolder; the tiers never share numbering. The retired repo-wide `docs/adr/` is gone — all ADRs are ticket-local.
