# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

This repo is the **`afk` Claude Code plugin** — a chain of skills inspired by and built upon [Matt Pocock's AFK workflow and skills](https://github.com/mattpocock/skills), adapted to Nakisa's Jira + GitLab + Maven monorepo. **AFK = "away from keyboard":** the upstream idea was to spend focused effort up front on requirements + design, then let agents implement the whole thing autonomously with no human in the loop. The split is deliberate: **human-heavy at the edges, autonomous in the middle.** Design (grills → PRD → SDD → plan) and final acceptance (CR/Merge, smoke verdict review) are interactive; the implementation phase runs hands-off via **`/afk:autopilot`** — a sequential driver that executes every subtask in a fresh subagent (driven-mode `/afk:execute`), self-provisions the live app for `api`/`e2e`/adversarial verification, parks failures (and their dependents) while independent work continues, and ends at the feature smoke gate. Each stage can still be run interactively by hand — autopilot is the default for the middle, not the only way. The chain takes a feature from raw idea → grilled requirements → PRD → (optionally) **an interactively-crafted UI mockup** (`/afk:prototype`) → architecture → SDD → (optionally) **grilled verification scenarios** (`/afk:grill-verification` interviews → `/afk:to-verification-plan` writes `VERIFICATION-PLAN.md`: UI journeys + API scenarios) → a **local execution plan** (a `plan/` dir of subtask contracts, not Jira issues) → execution (`/afk:autopilot` hands-off, or `/afk:execute` per subtask by hand) → the **feature smoke gate** (`/afk:smoke-test` — full when a `VERIFICATION-PLAN.md` drove the plan, minimal otherwise; every plan has one).

The repo contains only the skills — workflow skills under `skills/afk/<name>/SKILL.md`, plus general-purpose utility skills (not part of the AFK chain) under `skills/utils/<name>/SKILL.md` — and the plugin manifests. The *work* the chain drives is Java/Maven inside a sibling core-services checkout. Jira (`mcp__jira__*`) is the tracker **only for the parent Enhancement/Bug** — `/afk:to-ticket` publishes the PRD there and `/afk:to-sdd` splices an SDD pointer; the subtask plan and its progress live entirely on disk. GitLab (`glab`) is the SCM.

There is no Python package, no test suite, and no build step — editing a `SKILL.md` and running `/reload-plugins` is the entire dev loop.

## Plugin layout & install

The plugin lives at `.claude-plugin/plugin.json` (manifest) + `.claude-plugin/marketplace.json` (local marketplace) + `skills/afk/<name>/SKILL.md` (AFK-chain skills) and `skills/utils/<name>/SKILL.md` (standalone utilities) — both dirs are declared in the manifest's `skills` array (which replaces the default `skills/` scan because the marketplace `source` resolves to the repo root). Install once via `/plugin marketplace add <repo>` + `/plugin install afk@nak-marketplace`, then persist via `enabledPlugins` in `~/.claude/settings.json`. After editing any `SKILL.md`, run `/reload-plugins` to pick up changes without restarting. See `README.md` for the full install snippet.

## How to write these skill files (treat prose like code)

These `SKILL.md` + sibling `.md` files are the program the agent runs — the same engineering discipline applies. KISS, DRY, YAGNI, modularization, in English:

- **Generic, never feature-specific.** A skill states the *mechanism*, not a story. No war-stories, no worked examples lifted from a real ticket/feature, no naming a concrete feature to illustrate a step. If an example is truly unavoidable, make it obviously hypothetical.
- **Downstream is blind to upstream.** A skill invoked later must not name the skill/stage that calls it or assume who ran first — what it needs arrives at invocation. Upstream may name its downstream; the reverse is the failure. (A steward/registry file may state its own read/write contract without naming callers — that's not a pipeline reference. Nor is gap-routing: a skill that detects a gap it doesn't own may name the skill that owns fixing it as a bounce target — what stays forbidden is naming or assuming who *called* it.)
- **DRY — one fact, one home.** State each fact (an enumeration, a format, a recipe, a rule) in exactly ONE file — its owning file — and have every other skill *point* to that file by path, never restate it. The agent running the pointing skill reads the pointed-at file anyway, so a copy is pure duplication that silently goes stale. E.g. `/afk:grill-requirements` says "go through the staples in `STAPLES.md`"; it does **not** list the staples — the list lives in `STAPLES.md`, which that agent reads regardless. Where the Lockstep section sanctions a synchronized copy (an emitter or parser needs the literal grammar/section shape), the copy is legal only at the emitting/parsing site and is tagged with its owning file — every other mention is a pointer.
- **Lazy load / progressive disclosure.** Surface an instruction only where the agent needs it. Keep `SKILL.md` to the trigger + the spine; push detail (formats, long checklists, procedures) into sibling `.md` files loaded on demand (the existing `[X.md]` pattern). Don't front-load what only one branch needs.
- **Single-writer artifacts** — one steward writes a shared on-disk artifact, every other skill reads (see "Section ownership invariants"; don't restate the ownership map here).

## Human followability (binding on every skill)

The workflow's speed is worthless if the human can't stay on top of it. Two plugin-root files govern this; skills point at them, never restate them:

- **`REPORTING.md`** — the reporting protocol: every terminal status line is followed by one jargon-free `In plain terms:` sentence + a pointer to the full story; notifications never carry a bare status token; abbreviations expand at first use. Any skill that emits `OUTCOME:` / `AUTOPILOT:` / `REVIEW:` / `ADVERSARY:` lines follows it.
- **`GLOSSARY.md`** (plugin root) — the one home for workflow-methodology vocabulary (L1–L9 legend, modes, states, verdicts, artifact names). Domain vocabulary stays in the target repo's glossaries. A skill that needs one of these terms defined points here.

The followability artifacts and their stewards: the **ticket index** (`INDEX.md`, read-this-first dashboard — created by `/afk:to-prd`, each later synthesis skill upserts only its own row), the **journal** (`plan/JOURNAL.md`, append-only event log — seeded by `/afk:to-subtasks`, appended to by `/afk:execute`, `/afk:autopilot`, `/afk:smoke-test`; append-only is the one sanctioned multi-writer pattern), the **review rollup** (`plan/review/INDEX.md`, owned by `/afk:review`), the **trace matrix** (`plan/TRACE.md`, emitted once by the terminal sync-harness subtask), and the **grill log** (`GRILL-LOG.md`, one section per grill skill).

## Context protection (binding on every skill)

The orchestrating agent's context window is the run's scarcest resource. **`DELEGATION.md`** (plugin root) owns the doctrine: the must-delegate triggers (bulk reads, repo-wide searches, suite/build runs, large diffs, external intake), the spawn rules (parallel-in-one-message, named agent types, nesting cap), the return contract (terse cited digest, bulk evidence to a file), and what must never be delegated (the human conversation, conversation synthesis, single-writer stamps). Skills point at it, never restate it. A step that matches a trigger delegates even where a skill's own prose predates the doctrine.

## The skills

- **Mandatory chain**: `/afk:to-prd` → `/afk:to-ticket` → `/afk:to-subtasks` → `/afk:autopilot` (or `/afk:execute` per subtask by hand) → `/afk:smoke-test`. `/afk:to-ticket` is the one step that publishes the local PRD to the parent Enhancement (the only design-chain skill that writes to the tracker). `/afk:to-subtasks` emits a **local plan** (`plan/PLAN.md` index + `plan/NNNN-slug.md` per subtask) — no Jira. `/afk:autopilot` runs the subtasks hands-off (or you run `/afk:execute` yourself, once per subtask); either way the executor advances each subtask's row in the local progress tracker. `/afk:to-subtasks` always seeds one terminal `NNNN-sync-harness` doc subtask (blocked by every other subtask, run last by `/afk:execute`) that syncs the CLAUDE.md harness for the shipped feature **and settles the staples registry** by delegating to `/afk:claude-md`.

**Staples registry.** A *staple* is a delivered capability that became a standing expectation (e.g. deep-linking, Excel import/export): once it exists, every future feature whose work matches its trigger must consider adopting it. Staples live in a per-service `{service}/STAPLES.md` registry (self-documenting format + the staples themselves) — **stewarded solely by `/afk:claude-md`** (the third steering-artifact it owns, alongside CLAUDE.md and `.claude/rules`) and read-only everywhere else. Two loops thread it through the chain: **consult** on the design side — `/afk:grill-requirements` matches each `active` staple's trigger and grills in/out (and raises new-staple candidates), `/afk:to-prd` records the call as acceptance criteria + a requirement ADR and carries the candidate, `/afk:grill-solution`/`/afk:to-sdd` design the accepted ones, `/afk:to-subtasks` turns them into Acceptance bullets + seams so `/afk:execute` builds them, `/afk:review` (spec-fidelity) checks they were honoured; **capture** on the delivery side — the `NNNN-sync-harness` subtask makes the authoritative call on candidates and advances Reference exemplars. Reshaping a `STAPLES.md` field touches only `/afk:claude-md` (the writer); the consulting skills point at the file, so they don't restate its shape.
- **Optional design layer**: `/afk:grill-requirements` (raw-idea grilling; maintains `GLOSSARY.md` only — no decision records) → `/afk:to-prd` (PRD + requirement ADRs under `.../adr/requirements/`; **local artifacts only — does not touch the tracker**) → (optionally) `/afk:prototype` (an **interactive UI-crafting loop**, not a grill and not a one-shot producer: reads the PRD User Stories, anchors to the **real frontend's** components + tokens, writes self-contained HTML the user opens and refreshes, and reshapes it live as the conversation goes; self-gates `no_ui` for backend/API/refactor features; durable-lite output — the won direction is `PROTOTYPE.md` + chosen HTML sibling to the PRD, traceable to User Stories so `/afk:grill-verification`'s UI journeys trace to it, losing scaffolding discarded; **local-first**, with a **frictionless opt-in** push to a persistent, team-shareable `claude.ai/design` project that is a share mirror only — the in-repo `PROTOTYPE.md` stays canonical) → `/afk:grill-solution` (top-down L1→L9 interview — L9 = implementation-seam walk + parallel compatibility audit vs the existing code) → `/afk:to-sdd` (writes `SDD.md` + per-decision design ADRs under `.../adr/design/` sibling to the PRD; owns the `## SDD` section of the parent Enhancement description) → `/afk:to-design-brief` (optional digest: synthesizes PRD + SDD + ADRs into a 1-2 page `DESIGN-BRIEF.md` for stakeholder review and pre-SDD reading; **repo-only — does not touch the tracker**, shared with stakeholders out of band). Recommended for new complex features; skip for small bugs / refactors / tooling.
- **Optional verification design**: `/afk:grill-verification` (interview) → `/afk:to-verification-plan` (synthesis). `/afk:grill-verification` interviews the user to design the feature's verification scenarios across **two modalities** — it writes only its `GRILL-LOG.md` checkpoint section (a grill, like `/afk:grill-requirements` and `/afk:grill-solution`); `/afk:to-verification-plan` then synthesizes the settled scenarios into `VERIFICATION-PLAN.md` sibling to the PRD: **UI journeys** (the real browser flows that decide "this feature works", traced to PRD User Stories) and **API scenarios** (direct-REST checks proving the backend contract for API/MCP callers who bypass the UI, traced to SDD §3 endpoints). Walking them concretely routinely surfaces PRD/SDD gaps. **UI journeys** can be designed after `/afk:to-prd`; **API scenarios need the SDD's §3 endpoint contracts**, so a pre-SDD run designs UI journeys only and defers the API section — re-run both skills after `/afk:to-sdd` to add it (`/afk:to-verification-plan` **appends**, preserving the UI section). **Local-only — no tracker.** Its plan is what makes `/afk:to-subtasks` emit the smoke gate + a build subtask per modality. The how-to-build-the-tests recipes are **not maintained in this repo** — they live canonically in the payable repo at `11700-payable/verification/ui-e2e/AUTHORING.md` and `11700-payable/verification/api/AUTHORING.md` (versioned with the verification code so they can't drift); every AFK skill only **points** at them by path, never embeds a copy.
- **Feature gate (always present)**: `/afk:smoke-test` — the **feature-level** completion gate (distinct from `/afk:execute`'s per-subtask `api` / `e2e/browser` tiers). It **only executes** already-built checks — it authors nothing. Every plan carries a gate: the **full** gate when a `VERIFICATION-PLAN.md` (from `/afk:grill-verification`) drove `/afk:to-subtasks` to emit a `## Feature smoke gate` in `PLAN.md` plus a terminal build subtask **per modality** — `NNNN-smoke-e2e` (UI journeys → `Scenario`s in the `11700-payable/verification/ui-e2e` Cucumber+Playwright catalog, per `…/ui-e2e/AUTHORING.md`) and `NNNN-smoke-api` (API scenarios → `node:test` `*.test.mjs` in `11700-payable/verification/api` using `../core`, per `…/api/AUTHORING.md`) — reviewed as code; env-limited scenarios like `@sap` / GL-post are tagged and excluded from the gate's green verdict. After **every** subtask is `done`, `/afk:smoke-test` runs both modalities (`npm run smoke` + `node --test`) against a **running app** and, only on green across both, stamps `Feature: complete` in `PLAN.md`. The same suites are reused by CI / scheduled / manual runs. It merges nothing and writes no Jira. Features **without** a `VERIFICATION-PLAN.md` get the **minimal** gate instead (`## Feature smoke gate (minimal)`: compile / app-start / regression / existing-suites — template in `skills/afk/to-subtasks/SMOKE-GATE.md`); its green stamp says `(minimal gate)` so it's never mistaken for scenario-verified.
- **Hands-off driver**: `/afk:autopilot` — walks the whole plan in rank order (Blocked-by respected), one fresh subagent per subtask running `/afk:execute` in **driven mode** (its prompt template is `skills/afk/autopilot/SUBAGENT-PROMPT.md`), self-provisions the live app per slice (`.claude/hooks/app-start-gate.sh` in the core-services checkout), parks failed subtasks + their dependents while independent subtasks continue (push notification on every park, per `REPORTING.md`), appends run-level events + a per-subtask heartbeat to `plan/JOURNAL.md`, then runs `/afk:smoke-test`. Sequential v1 — no parallel subtasks. It writes no PLAN.md cell (single-writer stays with the executor); commit+push per subtask on the feature branch is authorized only inside its runs.
- **Adversarial execution gate**: `/afk:adversary` — `/afk:execute` Step 10.5. A fresh session probes the **running app** with scenarios derived from the contract + specs under a hard information diet (never the diff / implementor tests). Verdict `clean`/`findings`(classed)/`tainted`/`env_unreachable`; blocking findings route by `class` like review findings and share Step 10's 2-cycle remediation cap; terminal → `adversary_fail`. Lockstep: change `/afk:adversary`'s verdict set or finding classes and you update execute Step 10.5's gate logic in the same commit.
- **Tooling**: `/afk:tdd` (red-green-refactor doctrine, invoked from `/afk:execute` Step 5). `/afk:review` (**independent post-verification review gate** — fresh, parallel subagents, one per concern, check the slice diff against the applicable CLAUDE.md chain, the spec/acceptance contract, and senior-engineer code-quality + refactor-safety bars; **read-only** — it returns a ranked findings report + a `clean`/`advisory`/`blocking` verdict and never edits/commits; invoked from `/afk:execute` Step 10, also runnable standalone as `/afk:review {NNNN-slug}`). `/afk:fix` (disciplined bug-fix orchestration — wraps `/afk:diagnose` + proportional `api`/`e2e` coverage + a Phase-2.5 **escape analysis** of the existing test that should have caught the bug + feature-session artifact reconciliation + a Phase-3.5 **workflow-feedback handoff** (`/afk:handoff`) for AFK-delivered features so the chain stops repeating the miss; routed from `/afk:execute` Step 8 on a stuck verification tier **and from the Step 10 review gate on a `correctness`/`spec` blocking finding**, also run standalone for ad-hoc bugs).

`/afk:to-subtasks` slices in **cited mode** when an SDD is present (each subtask references binding SDD sections + ADRs, lists the §9b seams it implements/uses, and carries a Conflict procedure block) and in **uncited mode** otherwise (PRD-only; human-gated per ticket). Mode is set by what's upstream: PRD + SDD (from `/afk:grill-solution`) → cited; PRD only (from `/afk:grill-requirements`) → uncited.

## Lockstep: the subtask plan contract

The plan is the load-bearing interface between `/afk:to-subtasks` (emitter) and `/afk:execute` (parser + progress writer). It is entirely on disk: `plan/PLAN.md` (the index — solution map, seam register, progress tracker) + one `plan/NNNN-slug.md` contract per subtask, sibling to `PRD.md`/`SDD.md`. A subtask's **id** is its filename stem (`NNNN-slug`); there are no Jira keys in the plan. If you add, rename, or change a section, update **both** `skills/afk/to-subtasks/SKILL.md` (the "Subtask contract" emitter) and `skills/afk/execute/SKILL.md` (Step 1 parser) in the same commit — they live in the same repo specifically so this lockstep is enforced by a single commit. Likewise the outcome status set (now including `adversary_fail`): if you broaden it, update the status list in `/afk:execute` Step 13, the autopilot park handling, and any skill that references it. The smoke gate now has two shapes — full (`## Feature smoke gate`) and minimal (`## Feature smoke gate (minimal)`) — with the same three-way lockstep: `to-verification-plan` emitter (full only), `to-subtasks` seeder (both, incl. the minimal-gate template in its SMOKE-GATE.md), `smoke-test` reader (both). The independent review gate is its own lockstep pair: `/afk:execute` Step 10 invokes `/afk:review`, gates on its `clean`/`advisory`/`blocking` verdict, and routes `blocking` findings by `class` — change `/afk:review`'s verdict set, its `class` enum, or its concern list and you must update Step 10's gate logic in the same commit.

The contract's base sections: `## Goal / Scope / Acceptance / Verification / Parent PRD / Blocked by / Implementation Notes`. `## Verification` is a **tiered table** (static → unit → integration → api → e2e/browser, where `api` is a direct-REST endpoint check via `11700-payable/verification/api` + `../core`); the implementor must turn every declared tier green. Cited mode adds six: `## Design refs / Seams / Produces / Parent SDD / Consumes / Conflict procedure`.

`/afk:execute` owns the PLAN.md progress tracker's `Status` column (`pending` → `designing` → `developing` → `verifying` → `reviewing` → `done`, or `blocked(<reason>)`) — one cell per run — plus each subtask file's `## Implementation Notes` block. `reviewing` is the independent review gate (Step 10); a gate that stays `blocking` after two remediation cycles sets `blocked(review_fail: …)`. Everything else in the plan is the human's.

## Cited-mode contract

The contract is enforced at three checkpoints — drift is impossible to ship without surfacing somewhere:

1. **Slicing time (`/afk:to-subtasks` Validation).** Checks (a)–(d):
   - **Graph validation (a)** — every `## Consumes` line resolves to a `## Produces` bullet on a subtask earlier in rank order. Forward refs / orphan consumers / multi-producer collisions all bounce.
   - **Anchor quality (b)** — every `## Produces` `{grep-anchor}` is checked against (i) a forbidden-generic-token list (`class`, `interface`, `void`, `function`, `def`, `method`, `struct`, `enum`, `type`, `record`); (ii) length ≥12 chars; (iii) trial `ctx_search` against `{file}` at HEAD must return ≤1 match. Ambiguous anchors that would fail-open at runtime are rejected at declaration time.
   - **Acceptance citations (c)** + **seam coverage (d)** — every cited Acceptance bullet ends with a resolving citation tag; every SDD §9b seam appears in the seam register with a named implementer that lists it `implement:` and carries its seam-test as a `## Verification` row.
2. **Consumer preflight (`/afk:execute` Step 2).** Reads `## Design refs` and `## Parent SDD` to load binding SDD/ADR context. Then for each `## Consumes` line `{PRODUCER-ID} {file}#{grep-anchor}`, reads `{file}` and greps for `{grep-anchor}`. A miss exits `contract_mismatch` carrying the producer id (no retry; record on both consumer and producer subtask files + set both tracker rows `blocked`). A binding-decision break exits `design_conflict` (no retry; routes to `/afk:grill-solution`).
3. **Producer self-preflight (`/afk:execute` Step 9).** Right before declaring `success`, the subtask greps each of its own `## Produces` anchors on the branch. A miss exits `produces_drift` (no retry; route the human to fix the impl OR re-emit the slice). Without this step, signature drift would surface only at the next consumer's preflight — surfacing the failure on the wrong subtask.

`## Produces` is mandatory on every cited subtask, even leaves with no consumer — it doubles as the reviewer's cheat-sheet, the producer-self-preflight grep target, the `static`-tier grep target, AND the next subtask's consumer-preflight grep target.

## Section ownership invariants (don't violate)

- **Parent Enhancement description**: the PRD content is authored by `/afk:to-prd` (on disk) and published into the parent — as the full inlined body in native Jira formatting (ADF), inside an AFK-managed sentinel block — by `/afk:to-ticket`, which preserves all content outside that block. `## SDD` (when present) is owned by `/afk:to-sdd`. (The Design Brief is **not** published to the ticket — `/afk:to-design-brief` is repo-only.) Other prose belongs to the human. (Subtask progress is **no longer** spliced into the parent — it lives in the local `plan/PLAN.md` tracker.)
- **MR description**: the `<!-- afk:subtasks:start --> ... <!-- afk:subtasks:end -->` checklist block is auto-maintained by `/afk:execute`; everything outside is preserved verbatim.
- **The local plan (`plan/`)**: `/afk:execute` owns only the PLAN.md progress-tracker `Status` cell of the subtask it is running (+ the `Last updated` date) and that subtask file's `## Implementation Notes` block. **`/afk:smoke-test`** owns a disjoint slice of the same PLAN.md — the `## Feature smoke gate` table's `Status` cells, its `Last run` line, its append-only `Run history` lines, and the header `Feature:` line — and nothing else. **`plan/JOURNAL.md`** is append-only multi-writer (`/afk:execute`, `/afk:autopilot`, `/afk:smoke-test` append; nobody edits or deletes a prior line; format owned by `skills/afk/to-subtasks/JOURNAL-FORMAT.md`). **`plan/review/`** (reports + `INDEX.md`) is owned by `/afk:review`, with `/afk:adversary` writing its report files there under its own naming. **`plan/TRACE.md`** is written once by the terminal sync-harness subtask.
- **The ticket index (`INDEX.md`)**: created by `/afk:to-prd` (which owns the summary paragraph and seeds every row); each synthesis skill upserts **only its own row(s)** of the artifact table (format + row-ownership map: `skills/afk/to-prd/INDEX-FORMAT.md`). Rows for artifacts a feature never produces stay `—`.
- **The grill log (`GRILL-LOG.md`)**: one `##` section per grill skill, each grill writes only its own section (format: `skills/afk/grill-requirements/GRILL-LOG-FORMAT.md`).
- The plan's contract sections must round-trip losslessly. If you add a section, update both the `/afk:to-subtasks` emitter and the `/afk:execute` parser together (see Lockstep above); a section read by `/afk:smoke-test` (the gate) must be updated in lockstep with that skill too. The `## Feature smoke gate` is seeded from `VERIFICATION-PLAN.md` (written by `/afk:to-verification-plan` from a `/afk:grill-verification` interview, covering both UI journeys and API scenarios) and the build-subtasks' authoring recipes are the verification repo's `11700-payable/verification/{ui-e2e,api}/AUTHORING.md` (referenced, never copied) — change a gate field's shape and you touch all three (`to-verification-plan` emitter, `to-subtasks` seeder, `smoke-test` reader) in the same commit.

## Skill ↔ human ownership split (CR/Merge)

`/afk:execute` drives the progress-tracker status (`designing` → `developing` → `verifying` → `reviewing` → `done`), the TDD loop, the verification tiers, the independent review gate (`/afk:review`, Step 10), commits, push, the MR checklist, and the subtask's Implementation Notes — then **stops**. It does NOT merge the MR. The human reviews the Draft MR and merges (and writes any gate fields) out of band. Auto-merging is outside the skill's lane — preserve this boundary when editing `/afk:execute`.

## Tracker boundary

`/afk:to-prd` produces **local artifacts only** (PRD.md + requirement ADRs on disk); it does not create or update any Jira/GitLab issue. Publishing the PRD to the tracker is the job of **`/afk:to-ticket`**: it publishes the **full PRD content** into an **existing** parent ticket's description as native Jira formatting (ADF — Jira Cloud), with any `mermaid` blocks rendered to PNGs **locally**, attached, and embedded inline as media nodes (the verified media-UUID method; no diagram source leaves the network). It is **idempotent** — the PRD lives in an AFK-managed sentinel block, so re-running updates in place and replaces prior `afk-fig*` attachments rather than duplicating; content **outside** the managed block (product-owner prose) is preserved verbatim unless the existing description is barebone. The intricate formatting/diagram/merge work is codified in `skills/afk/to-ticket/scripts/publish_prd.py` for deterministic behavior (it reads Jira creds from env or `~/.claude.json` and talks to the REST API directly, since attachment upload has no MCP tool). It deliberately **does not** create the parent (refuses without `parent_key`), sets **no label**, creates **no GitLab branch** (`/afk:execute` self-creates its branch), and publishes **PRD content only** — not the SDD/Design Brief. Only **`/afk:to-ticket`** (PRD body) and **`/afk:to-sdd`** (its `## SDD` pointer section) write to Jira; everything else stops at disk or GitLab. `/afk:to-prd`, `/afk:grill-verification`, `/afk:to-verification-plan`, `/afk:to-subtasks`, and `/afk:to-design-brief` are **local-only**; `/afk:prototype` is **local-first and tracker-free** — its canonical output (`PROTOTYPE.md` + chosen HTML) is on disk, and its **only** network egress is an **opt-in** `claude.ai/design` push (a share mirror, never Jira/GitLab/merge); `/afk:execute` touches **GitLab** (push + Draft MR) and the local plan, but **not Jira** — subtasks are local artifacts and their progress lives in `plan/PLAN.md`. `/afk:grill-verification` writes only its `GRILL-LOG.md` checkpoint section (it only interviews otherwise); `/afk:to-verification-plan` writes only `VERIFICATION-PLAN.md` (+ gap notes) on disk. `/afk:smoke-test` is **local-only too**: it runs the verification suites (UI + API) against a target app and edits only its slice of `plan/PLAN.md` (the `## Feature smoke gate` Status cells + `Feature:` line) — no Jira, no GitLab push, no merge.

## Conventions to keep

- **Branch names** must match the GitLab regex `^[a-z0-9][a-z0-9/\-\.]*$` — the `kapteyn/development/{username}/{enh_id_lower}` pattern is load-bearing for `/afk:execute`'s push.
- **Two ADR tiers, separate subfolders.** Requirement-level ADRs (what/why) live in `.../{TICKET-ID}/adr/requirements/NNNN-*.md` and are owned by `/afk:to-prd`. Design-level ADRs (how) live in `.../{TICKET-ID}/adr/design/NNNN-*.md` and are owned by `/afk:to-sdd`. Numbering is local to each subfolder; the tiers never share numbering. The retired repo-wide `docs/adr/` is gone — all ADRs are ticket-local.
