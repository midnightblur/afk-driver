1.1Map: Critical aspectsran twiceeven running twice is not reliable as a flaky test can also pass in both run. is it necessary? it is costing double but does not fully address the issue

You are right. 2 passing runs do not prove a test is stable, and they double the cost of the slowest tests. My proposal in place of it: each high-level test runs once. Only a failure runs once more. A fail followed by a pass counts as flaky, which is a fail: the test goes back to the builder with the rerun check named. A pass is not rerun. The judge also looks for the signs of a flaky test for each level, from the test levels table: fixed sleeps, selectors tied to the page structure, shared data, and a dependence on test order. That catches a flaky test that passed by luck, which a second run cannot do. The usual cost is 1 run. This changes a settled requirement (PRD AC-022), so after this design session I correct the PRD through a short return to the grill, and the two stay in agreement.
