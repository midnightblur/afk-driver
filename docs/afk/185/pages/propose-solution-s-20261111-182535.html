1.1Map: Critical aspectsran twiceeven running twice is not reliable as a flaky test can also pass in both run. is it necessary? it is costing double but does not fully address the issue

You are right. 2 passing runs do not prove a test is stable, and they double the cost of the slowest tests. My proposal in place of it: each high-level test runs once. Only a failure runs once more. A fail followed by a pass counts as flaky, which is a fail: the test goes back to the builder with the rerun check named. A pass is not rerun. The judge also looks for the signs of a flaky test for each level, from the test levels table: fixed sleeps, selectors tied to the page structure, shared data, and a dependence on test order. That catches a flaky test that passed by luck, which a second run cannot do. The usual cost is 1 run. This changes a settled requirement (PRD AC-022), so after this design session I correct the PRD through a short return to the grill, and the two stay in agreement.

Round 1 What the ticket says For your information

#185: afkv2 verification: propose-verification (medium lane) + small lane, highest-value test level with proof

The ticket text

Pain

An agent added a clickable Jira ticket URL to a lavish page, declared the job done, and the link did not work. The agent never ran the changed behavior through its real entry point. Nothing in afkv2 made it.

Goal

Verification runs automatically in every development task: a small bug fix, a small enhancement, a full feature. Anything testable is tested, with proof, at the highest-value level at minimum:

  • testable through a UI → test it through the UI;
  • testable through an API → test the API;
  • testable at contract level → contract (Pact) test.

The bigger the task, the more levels of tests (unit to UAT).

Scope

1. **Medium lane — /afkv2:propose-verification**: port v1 grill-verification in the afkv2 lean spirit (remove frictions and blockers, instructions over scripts). Agents research, investigate, multi-provider proposers draft and debate, then propose a final verification plan. The human sees the full plan, high to low level, on the lavish page and steers it — no grilling form. The plan is executed in subtasks during development and at the end before ship. 2. Small lane: bring the half-built v1 small lane (branch feat/feat-small-lane, docs/afk/small-lane/) to v2 in the same spirit. Human and agents still talk through the issue, the expected fix and how to test it, even if only for a few minutes.

Evidence found (round 0)

  • v1 chain: grill-verification → VERIFICATION-PLAN.md → to-subtasks smoke gate → smoke-test. Script-gated; no highest-value-level rule; no contract (Pact) testing.
  • v1 small lane: bugs only; diagnose/fix split with approval; proof = failing-then-passing test, all tiers, live before/after. 6 of 13 subtasks done; two review stalemates.
  • afkv2 (feat/afkv2): medium lane only; propose-verification planned for P1 and small lane for 2.1 (docs/afk/afkv2/PRD.md); the autopilot done check verifies the TDD verdict and Produces anchors but never records Verification rows; not applicable: accepts any reason; no feature-level gate; change-request proofs are unchecked free text.
