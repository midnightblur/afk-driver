R-2 L1 — Keep the single local page runtime Decided open l1-topology

The deployment and runtime topology is inherited.

Decision

Keep one local page engine that produces static HTML for the existing browser host; add no service or network boundary.

Why this one

The inherited topology meets the access and no-hover-request requirements with no new deployable unit.

Other options considered (rejected)

  • Add a tooltip service or browser endpoint; rejected because all source data already exists in the page artifact and hover must make no request.

R-2 L3 — Store typed term and ID entry arrays Decided open l3-data

Page JSON remains the source of truth; HTML stores a derived source block.

Decision

Add optional page/1 tips.terms[] and tips.ids[] arrays; validate field shape in schema and reference or collision rules in engine invariants.

Why this one

Typed arrays preserve invalid duplicate input for precise errors and cover every page element uniformly.

R-2 L4 — Keep local plain-text resolution under a measured budget Decided open l4-quality

The accepted large-data option sets the numeric posture.

Decision

Resolve tips locally as plain text; allow any catalog count; require 2,000 tips over 200,000 visible characters to scan and rescan within 1,000 ms on the CI runner, after the existing 300 ms debounce.

Why this one

A measured budget controls cost without rejecting a valid page solely by catalog count.

Other options considered (rejected)

  • Reject catalogs above 2,000 entries; rejected by the human in a-large-data because count should not define validity.
  • Leave performance unmeasured; rejected because the regex and DOM walk scale with input.

Evidencespec

Human choice a-large-data; afkv2/engine/shell/tips.js:8-18,31-60,264-270

To undo

Add a hard limit only after measured failure and a requirements decision on oversized pages.

R-2 L5 — Centralize page-tip invariants Decided open l5-domain

The page owns meanings; the engine guards validity; the runtime guards precedence.

Decision

Make schema validation the guardian of entry shape, engine content validation the guardian of references and collisions, and one runtime resolver the guardian of precedence and text safety.

Why this one

Each invariant has one guardian at the earliest boundary that has the required information.

Other options considered (rejected)

  • Let each component renderer validate and resolve its own tips; rejected because rules and errors would drift.
  • Let flat dictionary merge order define precedence; rejected because lowercase IDs lose exact-case identity.

R-2 L6 — Embed a durable source block, then derive runtime data Decided open l6-process

Render and reopen must produce the same tip payload.

Decision

The page builder emits a typed page-tip source block outside the replaceable runtime marker; render and HTML reopen both combine that source with shared terms, while page/0 alone may read the legacy sidecar.

Why this one

A durable embedded source survives reinjection and keeps arbitrary-HTML opening compatible.

Other options considered (rejected)

  • Store page tips only in the replaceable injected block; rejected because reopen deletes and rebuilds that block.
  • Read sibling page JSON when HTML opens; rejected because the launcher also opens arbitrary HTML.

How should page-owned tips evolve across design rounds? Recommended: A.

A — A — page-wide current meaningB — B — round snapshots

One mutable page catalog serves every round. Earlier visible text gets the latest corrected tip. Cost: old hover wording is not a snapshot.

Each round keeps its tip meanings. Cost: duplicate data, round-aware resolution, and more complex cross-round precedence.

Both choices preserve settled card text, but they give archived hover text different audit meaning. Code evidence cannot choose that product trade-off.

How should the design bound large tip catalogs? Recommended: A.

A — A — measured budget, no count capB — B — schema count cap

Require 2,000 total tips over 200,000 visible characters to finish first scan and a debounced rescan within 1,000 ms on the CI runner. Keep fields at 1–128 key characters and 1–1,000 value characters.

Use the same timing target and field limits, and refuse more than 2,000 total tips. Gives a hard ceiling but makes catalog size part of page validity.

The runtime cost is linear but unmeasured, and the PRD sets no valid catalog maximum. A hard cap could reject a legitimate page.
