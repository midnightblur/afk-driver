Working session · pitch + field guide

Ship features while away from keyboard — without trusting the agent.

AFK is a Claude Code plugin that turns coding agents into a gated pipeline. This track is the operator's manual: what each command actually does, what the gates check, what lands in your repo, and where it bites.

AFK is process engineering for AI-assisted delivery: independent verification, a complete audit trail, and a workflow that measures and improves itself. This track covers quality, throughput, governance, and what adoption costs.

dev · 01

What a feature feels like, hands-off

The honest version of a real run — green dots are your moments, amber dots are the machine's. Your keyboard time concentrates at the start (interviews) and the end (code review). The middle runs without you.

  • You · ~30–60 min

    Get grilled

    /afk:grill-requirements interrogates your idea against the service's GLOSSARY.md and staples until the requirements tree is exhausted. Then /afk:grill-solution walks the design top-down through nine layers — L1 topology to L9 implementation seams — and refuses to descend until each layer is settled. Feels like a design review with a colleague who never lets a hand-wave through.

  • Machine · minutes

    Synthesis

    /afk:to-prd and /afk:to-sdd write PRD, SDD, and one ADR per decision into the spec folder. Pure synthesis — if it wasn't settled in the grill, it can't appear in the doc.

  • You · ~15 min

    Approve the slicing

    /afk:to-subtasks slices into plan/NNNN-slug.md contracts. In cited mode every claim in a contract must cite the SDD/ADRs; producer↔consumer seams get registered in PLAN.md. You sanity-check the cut and the dependency edges.

  • Machine · hours, unattended

    Autopilot

    /afk:autopilot spawns a fresh subagent per subtask: design intent → TDD (red before green) → every verification tier the contract declares → the review gate → the adversary gate → commit → push → Draft-MR update. A failing subtask is parked with its dependents; independent subtasks keep executing. You get a push notification with the park reason, not a dead session.

  • Machine · gate

    Smoke, then preflight

    /afk:smoke-test runs the feature's ui-e2e + api suites against a live app, scoped by feature tags. On green, /afk:preflight merges master in (never rebases), re-validates, runs a fresh integrated review and final seam check under a hard 2-cycle fix cap, then babysits CI to flip the MR from Draft to Ready.

  • You · normal MR review

    Review with receipts

    The MR arrives with JOURNAL.md (what happened, in order), plan/review/ (review + adversary reports), and TRACE.md (acceptance criterion → subtask → commit). Merge stays yours — no skill can do it.

/afk:grill-requirementsstress-test the idea against the domain's own language

Interview loop against the domain GLOSSARY.md and the staples registry. Terms crystallise into the glossary as they settle; every checkpoint appends to GRILL-LOG.md so synthesis skills can cite it later. Interrogation only — no design happens here.

/afk:grill-solutionthe nine-layer architecture interview, strictly top-down

Interrogates the solution design one layer at a time, refusing to descend until the current layer is settled — so a low-level choice (say, a table schema) can never quietly predetermine a higher-level one (which service owns the data). The nine layers, which also become the SDD's section structure:

  • L1 — system topology: where the feature sits among services, UIs, and external systems.
  • L2 — service boundaries & integration: which service owns what; the endpoints and contracts between them.
  • L3 — data architecture: schema, storage, migration.
  • L4 — cross-cutting quality: security, transactions, observability, error handling.
  • L5 — domain model: entities, aggregates, invariants.
  • L6 — process & coordination: workflows, state machines, async jobs.
  • L7 — module decomposition: packages and modules inside the service.
  • L8 — tactical patterns: class-level design patterns and idioms.
  • L9 — implementation seams: the exact places in existing code the change plugs into — each verified against the real codebase, not assumed.

Questions are triaged into debate (alternatives worth weighing, asked one at a time) and confirm (safe defaults you accept or override in a batch) — so the interview is thorough without being exhausting. Settled decisions land in GRILL-LOG.md, ready for /afk:to-sdd.

/afk:to-prd · /afk:to-sdd · /afk:to-design-briefsynthesis skills — no new decisions allowed

to-prd writes PRD.md + adr/requirements/NNNN-*.md and seeds INDEX.md. to-sdd writes SDD.md + adr/design/NNNN-*.md (separate ADR numbering). to-design-brief compresses both into 1–2 pages for stakeholders. All disk-only; the single tracker writer on this side is /afk:to-ticket, which publishes the PRD into the Jira parent as native ADF with rendered diagrams — idempotent, re-run to update.

/afk:prototype · /afk:design-systemsettle UI against the real frontend's tokens

design-system (one-time per service) mirrors the live frontend into a shareable catalog of real tokens + archetype cards, fidelity-checked against the running app. prototype then crafts the feature's mockup as standalone HTML anchored to those components; self-gates no_ui when there are no net-new screens.

/afk:grill-verification · /afk:to-verification-plandesign the tests before the code — two modalities

Interviews the feature's verification scenarios in two separate modalities:

  • UI journeys (needs the PRD): browser flows proving user-facing behavior — actor and trigger, the concrete click-path, an observable definition of done, preconditions, alternate/error paths, and mandatory role-based / data-scope / input-validation rows (a "denied user" row is required, not optional).
  • API scenarios (needs the SDD): direct-REST checks proving the backend contract for callers that bypass the UI — only in play once the endpoint contracts exist to test against.

/afk:to-verification-plan then synthesizes the settled scenarios into VERIFICATION-PLAN.md, sibling to the PRD/SDD — re-run it after the SDD lands to append the API side. Downstream, these scenarios become the executable Gherkin suites the smoke gate runs.

/afk:to-subtasksslice into contracts; cited mode when an SDD exists

Emits plan/PLAN.md (index, tracker, seam register, smoke-gate declaration) + one NNNN-slug.md per subtask. Cited mode: every contract claim cites SDD/ADRs. Uncited mode (no SDD) is human-gated. A terminal NNNN-sync-harness subtask, blocked by all others, folds durable learnings into CLAUDE.md via /afk:claude-md. Slicing-time contract checks live in VALIDATION.md.

/afk:executeone subtask, end-to-end, stops at CR/merge

Design intent → TDD → every declared verification tier → review gate → adversary gate → commit → push → Draft-MR + PLAN.md updates. Two things it will never do: merge, and mark its own review verdict. Branch naming is enforced by a git-native hook that only fires for agent-created branches.

/afk:tddthe red-green-refactor doctrine every slice follows

Four stages: Planning (interface and behavior list — human-approved when run interactively, auto-approved when a subtask contract already defines them) → Tracer bullet (one first test taken red→green to prove the whole test rig works) → Incremental loop (one behavior at a time: failing test, minimal code to green) → Refactor (only ever on green). Done means: every planned behavior green, refactor pass done, module suite green. The red-first rule is the point — a test that has never failed proves nothing.

/afk:autopilotthe plan driver: fresh contexts, park-and-continue

Walks PLAN.md subtask-by-subtask, one fresh subagent each — no context bleed between slices. Provisions the live app for verification tiers that need it. Failure ⇒ park subtask + dependents, push-notify, continue independent work. Smoke-green ⇒ chains /afk:preflight. Sequential in v1 — no parallel subtasks yet.

/afk:mission-controlwatch a run live — read-only, derived, never a second home for status

Renders a per-feature HTML dashboard derived from the plan's existing artifacts — tracker, journal, gate verdicts, SDD diagrams, git diffs. Watch mode follows a live run; --once re-renders an already-finished feature retroactively (that frozen render is also what preflight commits as ship evidence). Deliberately a viewport, never a data store: agents keep writing the real artifacts, a renderer keeps the page true — so the dashboard can never disagree with the files. An Understanding panel tracks each feature's post-ship explainer artifact by parsing only its machine-readable header.

/afk:review11 concerns, fresh eyes, skeptic-verified findings

Parallel read-only subagents, one per concern. Seven always run — claude-md-compliance (violates a documented rule?), spec-fidelity (truly done — every acceptance bullet, every seam?), logic-correctness (bugs, edges, races), code-quality (the enumerated smells a senior dev would flag: dead code, duplication, god methods, leaky abstractions, poor naming, magic values, leftover debug logs, hardcoded secrets/tokens, TODOs left in), test-veracity (do the tests assert real output, or pass vacuously?), scope-and-impact (stayed in bounds; blast radius of changed symbols), refactor-safety (touched pre-existing code without breaking its other users?). Four more are trigger-activated when the change warrants a design-level look: design-quality, domain-alignment, resilience, api-contract. Each reviewer is deliberately blind to the implementor's reasoning and is handed exactly two documents: its own checklist file (one per concern under review/checklists/) plus a shared PRECEDENCE.md (baseline precedence, the pattern-debt rule, one-owner-per-smell, a mandatory open-question slot). Findings pass a skeptic check before they count; the caller gates on the verdict. Complemented by mutation-probe.sh for empirical test strength.

/afk:adversaryruntime probing on a hard information diet

Fresh session, sees the contract and specs only — never the diff, never the implementor's tests. Designs attack scenarios, executes them against the live app, returns a classed verdict with reproducible evidence. Catches what static reading structurally can't.

/afk:smoke-test · /afk:preflightfeature gate, then ship gate

smoke-test: runs the feature's browser ui-e2e + direct-REST api suites against a running app; green on both stamps the feature complete in PLAN.md. preflight: 7-step ladder — refuse without smoke-green, merge master behind an ancestry guard, re-validate, fresh integrated review + final seam check (shared 2-cycle fix cap), generate the feature's understanding artifact (advisory row — can never block the ship), commit ship evidence, babysit CI, flip MR to Ready. CI-only failures and secret-detection hits always park for a human.

/afk:understandthe post-ship explainer — teach the team what actually landed

Generates one team-shareable, fully offline interactive HTML artifact per feature, checked in at {spec-dir}/understanding/index.html. It explains the implementation as built — synthesized from the real diff (derived from the feature branch or the journal's pushed ranges, never guessed), the run journal, and the review records — not from the plan's intentions. Five sections: dual-depth background (skim or deep), the core intuition, a seam-ordered code walkthrough covering every changed file, notable plan-deviations (mined by joining review findings with their remediation outcomes, plus journal parks and pattern-debt rows), and an opt-in quiz.

Quality is gated the same way code is: mechanical checks first (fully offline, full-diff coverage, size cap, well-formed machine header), then a fresh-context skeptic that never saw the synthesis judges it against the format contract, with one revision allowed — then fail-soft rather than ship slop. Two modes: auto (runs inside preflight as an advisory step — a failure never blocks the ship; lands as one docs-only commit) and standalone (/afk:understand {plan-dir}, prompts for quiz size and depth, never commits). The mission-control dashboard's Understanding panel reads the artifact's machine header.

/afk:bug · /afk:fix · /afk:diagnosethe side door for bugs

bug capture snapshots a bug mid-task without losing your place and files it with evidence; dispatch hands it to an autonomous fixer in its own worktree that delivers a mergeable MR, auto-retested when the fix lands (10-state ledger under .claude/bugs/). fix orchestrates verification-phase bugs: root-cause via diagnose's reproduce→minimise→hypothesise loop, proportional regression coverage, escape analysis, spec reconciliation.

/afk:retro · /afk:claude-md · /afk:setupthe workflow maintains itself

retro mines journals, review rollups, adversary reports, park reasons, and gate-latency metrics into ≤5 evidence-cited proposals written as concrete plugin edits. claude-md stewards CLAUDE.md, role sidecars, rules, and staples. setup is the environment doctor; its audit mode catches dependency/doc drift before plugin changes ship.

dev · 06

The compounding loop — why it gets better every feature

The core philosophy: every feature must leave the system smarter than it found it. Not as a nice-to-have — the plan's terminal subtask is banking the lessons, so a feature isn't done until its knowledge is. Three accumulators do the compounding.

Feature entersgrill challenges it against everything already known
Glossary consultedterms mean one thing; staples resolved in/out
Build & shipgates enforce the accumulated rules mechanically
Lessons bankedsync-harness: new terms, new staples, new CLAUDE.md rules
Next featurestarts with a richer vocabulary, more obligations pre-checked

Glossary — shared language, earned once, reused forever

Terms are defined at the exact moment they're settled during the requirements grill — the rule is explicit: update the owning service's GLOSSARY.md as terms resolve; don't batch, capture as they happen. And the glossary is pure vocabulary by rule — no implementation details, not a spec, not a scratchpad. The payoff compounds: once "credit hold" or "posting run" means exactly one thing, every future conversation — human↔human, human↔agent, agent↔agent — gets more precise and shorter. Nobody re-explains, nobody quietly means something different, and an agent reading the word inherits the whole settled meaning for free.

Staples — cross-cutting obligations that can never be skipped silently

A staple is a delivered capability that became a standing expectation — audit logging, change detection, permission enforcement — registered in the service's STAPLES.md as Trigger → Obligation → Reference exemplar. Two rules make the registry bite:

  • Inbound: every requirements grill reads the registry first, and for each active staple whose trigger matches the feature, you must resolve it in or out — with a recorded rationale. The grill's exit gate blocks until every matching staple is resolved; silent skipping is structurally impossible.
  • Outbound (the mirror question): is this feature itself a new staple? If plausibly yes it's flagged as a candidate, and at delivery it gets registered — so every future feature will be asked about its implications, forever.

That mirror question is the compounding step: each cross-cutting capability you ship becomes a question the process asks automatically from then on.

The harness — knowledge lives where the work happens

Project memory isn't a wiki nobody reads; it's a hierarchy of CLAUDE.md files (repo root → service → directory) that agents load automatically, by proximity — work under a directory and its rules are simply in context, no lookup step to forget. Role sidecars (IMPL.md / TESTING.md / DEBUG.md) hang off them and load on demand, so implementation lore doesn't bloat every session. The doctrine is "steer, don't document": trust agents to read code; capture only what code won't reveal. A four-gate inclusion bar keeps it lean — a fact must be non-obvious, durable, steering, and not duplicated in an ancestor file; unsure → omit. And the rules you can't trust to be followed graduate into hooks: a convention becomes a script, and a script can't be ignored.

/afk:claude-md — the steward that closes the loop

One skill is the sole writer of all of this memory — the CLAUDE.md chain, the sidecars, the rules, and every STAPLES.md. It never writes unasked: always propose → approve → write, so the accumulated instruction set stays curated, deduplicated ("one fact, one home"), and trusted. Most learnings arrive through the terminal sync-harness subtask every plan ends with — blocked by all other subtasks, so banking the lessons is literally the last gate before a feature is finished. Above it, /afk:retro and per-bug escape analysis feed the same loop at the process level: the workflow edits itself with the same propose-and-cite discipline it imposes on code.

dev · 07

Subtask contracts & the seam register

The core trick against integration drift: subtasks don't share context, so their only agreement is written down — and checked mechanically, three times.

Each NNNN-slug.md contract declares what the slice produces (classes, endpoints, events — by symbol name), what it consumes from other subtasks, its acceptance criteria, and which verification tiers apply. Producer/consumer pairs are registered as seams in PLAN.md and verified by grep against the actual tree at:

  • Slicing — do the declared seams reference symbols the SDD actually defines?
  • Consumer preflight — before a consumer subtask starts: does the producer's symbol exist as declared?
  • Producer self-preflight — before a producer finishes: does everything it promised exist under the promised name?

For new-Java seams there's opt-in seam materialization — the interface is generated up front so the compiler enforces the contract; everything else stays on grep anchoring. Net effect, per the docs: "never a silent integration surprise."

Gates & hooks — the part that can't be persuaded

Skills are prompts; gates are shell scripts wired into Claude Code's Stop hook. They fire on every session stop in the repo — chain or no chain — and block the turn until satisfied. Pass results are cached (clean stops stay cheap); every firing logs latency to a JSONL metrics stream that retro reads.

dev · 10

Sharp edges you'll actually hit

  • v1 Autopilot is sequential — one subtask at a time even when the dependency graph would allow parallelism.
  • env Live app required for adversary, smoke, and app-start tiers — you need a bootable local/dev instance; provisioning is part of autopilot but the environment is yours to own.
  • scope Executable smoke suites exist only in payable (11700-payable/verification/); other services declare a minimal gate. app-start-gate defaults to the payable leaf.
  • env Single-identity e2e token minter — every role mints the same user, so role-scoped data-visibility can't be proven end-to-end; use direct aspect tests instead.
  • gap Seam materialization is Java-new-code only — existing-file and non-Java seams stay grep-anchored; a rename can still slip past until the next checkpoint.
  • policy Deliberate refusals: bug pipeline won't run hands-off; preflight never auto-fixes CI-only failures or secret hits; fix budget is a hard 2-cycle cap. When it parks, that's the design working.
  • new /afk:understand is freshly shipped — built and reviewed, currently on its feature branch pending merge. Full coverage in "The chain, fully" above.
  • meta No test suite for the plugin itself — dev loop is edit SKILL.md → /reload-plugins → dogfood; setup audit and retro are the drift catchers.
directors · 01

The case in one paragraph

Coding agents are already fast; unmanaged, they're fast at producing plausible-looking work that fails in integration, review, or production. AFK is the management layer: it converts agent output into gated, evidenced, auditable delivery — the same idea as CI/CD, applied one level up, to the act of building itself.

Quality

Nothing self-certifies. Every slice passes independent 7-concern review, adversarial runtime probing, and mechanical gates (compile, format, lint, wiring, mutation) that cannot be argued with. A feature is "done" only when its UI + API suites pass against a running app.

Speed

Human time concentrates where humans add value — requirements and design interviews, final code review. The build phase runs unattended, overnight-capable; one failure parks a slice, not the run.

Auditability

Every feature leaves a versioned folder: PRD, decision records, per-slice contracts, event journal, review + adversary reports, and a criterion→commit trace. "Why does it work this way" has a file, permanently.

Self-improvement

Three accumulators compound across features: a domain glossary (terms settled during requirements, so humans and agents communicate precisely with fewer words), a staples registry (cross-cutting obligations every new feature must explicitly resolve in-or-out — and each shipped capability adds itself to the list), and layered instruction files agents load automatically. Each feature banks its lessons before it may finish; a retro skill and per-bug escape analysis tune the process itself, on evidence, not anecdote.

directors · 02

How quality is enforced, not hoped for

Three independent layers, each catching what the previous one structurally cannot.

LayerMechanismCatches
Mechanical10 gate scripts on every session stop: compile, formatter, lint, orphan-artifact wiring, branch naming, app boot, mutation probe, doc genericity. Shell scripts — immune to persuasion.The cheap, frequent failures: broken builds, dead code, tests that assert nothing.
Independent reviewFresh agents, blind to the implementor's reasoning, across 11 concerns (7 always-on + 4 trigger-activated design-level: design quality, domain alignment, resilience, API contract) — each working its own written checklist file (the code-quality concern alone checks dead code, duplication, god methods, leaky abstractions, naming, magic values, debug logs, hardcoded secrets, leftover TODOs); findings verified by a skeptic pass before they count.Logic errors, spec deviations, quality erosion — the implementor grading its own homework is the failure mode this exists to kill.

Upstream of all three sits decision hygiene: requirements are interrogated against the team's domain glossary before anything is written, architecture is interviewed through nine layers before code, and every decision lands as a record with its rejected alternatives. Where the throughput comes from

  • Unattended execution: after the design interviews, the plan runs hands-off — one fresh agent per subtask, verification included, Draft MR maintained continuously. The engineer's calendar is blocked for interviews and final review, not for supervision.
  • Park-and-continue: a failing subtask is parked with its dependents while independent work proceeds; the engineer is push-notified with the reason. One bad slice no longer costs a night of runtime.
  • No rework loops from drift: producer/consumer seams between subtasks are declared and mechanically checked at three points — integration surprises, the classic multi-slice tax, are caught before they compound.
  • Bugs as throughput, not interrupts: a captured bug dispatches to an autonomous fixer in an isolated worktree and comes back as a reviewable MR with auto-retest — engineers aren't context-switched off feature work.
  • Honest caveat: the pipeline front-loads effort. Interviews and planning cost real hours before any code exists; the payoff is in reduced review churn, rework, and escaped defects. v1 executes subtasks sequentially, so wall-clock per feature has known headroom (parallel execution is the obvious next step).

The multiplier: one engineer, overlapping features

Because the build phase needs no supervision, a single engineer runs features like a pipeline — designing feature B while feature A builds, reviewing A while B builds, and so on. The engineer's time stays on the two stages where judgment matters; machine time fills the gaps, including overnight.

Governance & blast radius

  • Humans keep the irreversible steps: no skill can merge an MR. Code review and merge are explicitly human-owned; the pipeline stops at Ready.
  • Tracker write access is minimal: exactly 2 of 36 skills may write to Jira (PRD publisher, bug filer). Everything else writes to disk and GitLab drafts — an agent cannot corrupt the tracker.
  • Refusal is a feature: CI-only test failures and secret-detection hits always park for a human — never auto-fixed. Fix budgets are hard-capped (2 cycles at the ship gate), so an agent can't thrash indefinitely.
  • Complete audit trail: spec folder per feature, versioned with the code: requirements, decisions with alternatives, per-slice contracts, event journal, review/adversary evidence, criterion→commit trace — plus a team-facing interactive explainer of what actually shipped, generated per feature. Compliance-grade answerability for "who decided, what was verified, when".
  • Environment doctor: /afk:setup probes every external dependency against a manifest and repairs or guides; its audit mode catches drift before plugin changes ship — onboarding and upkeep are themselves automated.

Risks and limits, stated plainly

  • maturity v1, single-team. Sequential execution; smoke suites exist for one service; some defaults are hardcoded to it. Generalization is designed for but unproven.
  • people The interviews are the load-bearing wall. The pipeline's quality ceiling is set by how seriously the grills are taken; a team that rubber-stamps them gets well-documented mediocrity, faster.
  • cost Token and environment spend is real. Multi-agent review, adversarial probing, and unattended runs consume model budget; live-app verification needs environments per developer.
  • env Environment coupling. Built on one platform (Windows dev, GitLab, Jira, this monorepo's Maven/npm shape); a role-scoped test-identity limitation and an unbuilt test-data-provisioning capability (currently mid-design) bound what e2e can prove today.
  • meta The workflow itself has no test suite — its own drift is caught by an audit mode and the retro loop, i.e. the same discipline it imposes, applied to itself.
  • counterweight Failure posture is conservative: when uncertain, it parks and notifies a human rather than pressing on. The uncontrolled-agent scenario — silent bad merges to master — is structurally excluded (humans merge; agents can't).
